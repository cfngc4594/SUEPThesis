\subsection*{部署环境准备}
本系统基于 Next.js、Prisma、PostgreSQL 与 Docker 构建，适用于高校程序设计教学场景下的本地演示与功能验证。部署前应确保操作系统已经安装 Node.js、Bun、PostgreSQL 与 Docker，并保证判题所需的 \texttt{gcc:latest} 镜像可正常使用。若采用本地 Docker 模式，系统通过 \texttt{/var/run/docker.sock} 调用宿主机 Docker；若采用远程 Docker 模式，则需要额外配置远程地址、协议和证书路径。

\subsection*{环境变量配置}
项目根目录为 \texttt{/Users/kali/Public/Github/judge4c}。首次部署时可参考 \texttt{.env.example} 复制生成 \texttt{.env} 文件，并按实际环境填写数据库、认证和 AI 服务所需的关键参数。

\begin{verbatim}
cd /Users/kali/Public/Github/judge4c
cp .env.example .env
\end{verbatim}

至少需要确认 \texttt{DATABASE\_URL}、\texttt{AUTH\_SECRET}、\texttt{AUTH\_URL}、\texttt{DEEPSEEK\_API\_KEY} 等变量可用；若使用远程 Docker，还需补充 \texttt{DOCKER\_HOST\_MODE}、\texttt{DOCKER\_REMOTE\_PROTOCOL}、\texttt{DOCKER\_REMOTE\_HOST}、\texttt{DOCKER\_REMOTE\_PORT} 及相关证书路径。为了保证论文与项目演示的一致性，后续答辩时建议固定使用同一套环境配置。

\subsection*{数据库与种子数据初始化}
在完成环境变量配置后，可执行数据库迁移、Prisma 客户端生成与种子数据导入操作。当前项目已经提供迁移文件与种子脚本，可直接完成基础题目与配置数据的初始化。

\begin{verbatim}
bunx prisma migrate deploy
bunx prisma generate
bunx prisma db seed
\end{verbatim}

\subsection*{启动与运行验证}
开发环境可在安装依赖后通过 \texttt{bun run dev} 启动，生产可构建性可通过 \texttt{bun run build} 验证。若采用 Docker Compose 方式，也可以直接启动整套本地环境。应用默认访问地址为 \texttt{http://localhost:3000}。

\begin{verbatim}
bun install
bun run build
bun run dev
docker compose -f compose.local.yml up -d --build
\end{verbatim}

当前工程已经完成 \texttt{bun run build} 通过的验证，可作为系统具备运行可行性的直接依据；对应的本地运行界面与开发环境状态见正文图5-11。

\section{关键接口与核心代码片段说明}
\pdfbookmark[1]{附录C 关键接口与核心代码片段说明}{appendix:c}
\addcontentsline{toc}{chapter}{附录C\hspace{1ex}关键接口与核心代码片段说明}

\subsection*{判题入口接口说明}
判题入口对应源码文件为 \texttt{src/app/actions/judge.ts}，其中 \texttt{judge(problemId, language, content)} 方法负责用户身份校验、题目与测试用例检查、Docker 配置检查、Submission 创建、源代码归档上传、编译调用、运行调用以及容器清理等完整流程，是平台客观评测链路的核心入口。该接口将用户请求转换为受控判题任务，并统一管理提交状态的初始流转。

\subsection*{编译接口说明}
编译逻辑位于 \texttt{src/app/actions/compile.ts} 中的 \texttt{compile(...)} 方法。该方法根据语言类型生成对应的编译命令，将提交状态更新为编译中或编译错误/成功，并在失败时把编译器输出写回 \texttt{Submission.message}。这样，系统既能判断代码是否可以继续执行，也能为后续错误展示和 AI 辅助分析保留必要上下文。

\subsection*{运行与结果判定接口说明}
运行逻辑位于 \texttt{src/app/actions/run.ts} 中的 \texttt{run(...)} 方法。该方法按测试用例顺序为程序提供输入数据，并结合标准输出比对、退出状态、时间限制和内存限制判断最终结果，将提交分别归类为 AC、WA、RE、TLE、MLE 等状态。判题过程中同时记录 testcase 级别的结果信息，为提交详情展示和后续测试分析提供数据依据。

\subsection*{AI 辅助分析接口说明}
AI 分析逻辑位于 \texttt{src/app/actions/analyze-code.ts} 中的 \texttt{analyzeCode(...)} 方法。该方法在提交创建后异步执行，先创建 \texttt{CodeAnalysis} 记录，再通过 DeepSeek 模型对代码的时间复杂度、空间复杂度、整体质量、风格、可读性、效率和正确性进行结构化分析，并把结果写回数据库。由于分析任务与主判题流程分离，因此即使 AI 模块异常，也不会影响客观判题结果的生成。

\subsection*{核心数据模型说明}
核心数据模型定义于 \texttt{prisma/schema.prisma}。其中，\texttt{Problem} 负责题目基础约束，\texttt{ProblemLocalization} 负责多语言题面内容，\texttt{Template} 负责语言模板代码，\texttt{Submission} 负责提交记录及状态流转，\texttt{Testcase} 与 \texttt{TestcaseInput} 负责标准测试数据，\texttt{TestcaseResult} 负责用例级结果记录，\texttt{CodeAnalysis} 负责 AI 辅助分析结果存储。这一模型划分使题目组织、判题执行与分析反馈之间能够通过统一的数据结构协同工作。

统一测试题目为“1000 两数之和”，统一测试语言为 C，统一做法为保留系统默认模板，只替换 \texttt{twoSum(...)} 函数。

其中，\texttt{AC}、\texttt{CE}、\texttt{WA}、\texttt{RE}、\texttt{TLE} 五类样例主要用于支撑判题正确性测试；低效正确样例用于展示复杂度分析与优化建议；可读性较差但可通过样例用于展示代码风格与可读性评价能力。

\subsection*{AC 样例}
预期状态为 AC；该样例也可作为“低效正确代码”用于 AI 复杂度分析。

\begin{verbatim}
int *twoSum(int *nums, int numsSize, int target, int *returnSize) {
  for (int i = 0; i < numsSize; i++) {
    for (int j = i + 1; j < numsSize; j++) {
      if (nums[i] + nums[j] == target) {
        int *res = malloc(sizeof(int) * 2);
        res[0] = i;
        res[1] = j;
        *returnSize = 2;
        return res;
      }
    }
  }

  *returnSize = 0;
  return malloc(0);
}
\end{verbatim}

int *twoSum(int *nums, int numsSize, int target, int *returnSize) {

\subsection*{可读性较差但可通过样例}
预期状态为 AC；适合用于表6-5中的风格与可读性反馈案例。

\begin{verbatim}
int *twoSum(int *a, int n, int t, int *r) {
  int i = 0;
  for (; i < n; i++) {
    int j = i + 1;
    for (; j < n; j++) {
      if (a[i] + a[j] == t) {
        int *x = malloc(sizeof(int) * 2);
        x[0] = i;
        x[1] = j;
        *r = 2;
        return x;
      }
    }
  }
  *r = 0;
  return malloc(0);
}
\end{verbatim}
