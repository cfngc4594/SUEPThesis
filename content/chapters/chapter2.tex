\chapter{在线编程评测平台相关技术基础}

\section{自动判题机制}

在线编程评测平台的核心任务，是对用户提交的程序进行自动化、标准化和可重复的评价。其基本流程通常包括代码接收、编译构建、运行控制、测试数据校验和结果返回等环节。与人工批改相比，自动评测响应更快、标准更统一，也更适合大规模教学场景\cite{kurnia2001online,leal2003mooshak,ala2005survey}。

从评测逻辑上看，自动判题的本质是将用户程序放入受控环境中执行，并以标准输入、标准输出和测试用例为依据判定结果。常见结果包括编译错误、运行错误、答案错误、时间超限、内存超限和通过等。对于教学型平台而言，自动判题不仅要给出结果状态，还应尽量保存运行日志、错误信息和测试记录，以便教师分析学生提交情况，也便于平台后续生成更有针对性的反馈。

需要强调的是，自动判题的评价依据必须具有确定性和一致性。同一份代码在同一运行环境、相同测试数据和相同资源限制下，应得到稳定一致的结果。这一特征决定了在线编程评测平台在架构设计上必须优先保证环境一致性、执行隔离性和任务调度的可靠性，而不能把判题结果建立在不稳定的主观分析基础之上。

从教学应用角度看，自动评测平台的目标也不应只停留在代替教师给结果这一层面。Ihantola 的研究表明，自动评测还可以延伸到反馈形式、学生测试能力评价和学习材料迁移等方面\cite{ihantola2011automated}；Tran 的本科项目则体现了传统教学型 OJ 的常见思路，即优先完成题目管理、提交判题和测试用例组织等核心功能\cite{tran2013uoj}。这些工作说明，教学型评测平台首先要保证主链路可用，其次才有必要继续增强反馈能力。

近年来，围绕自动评分工具究竟评什么、怎么评以及评得是否可信等问题的系统综述进一步把讨论从功能实现推进到研究方法与证据链层面。Messer 等对 2017--2021 年间大量文献的分析显示，多数工具仍以正确性为主，但对可维护性、可读性与文档化等维度的关注仍不充分；同时，评估手段往往依赖问卷或与人工评分对照，公开数据集不足会削弱不同工具之间的可比性\cite{messer2024automated}。Paiva 等对计算机科学作业自动评测的综述则强调，静态分析与容器化正在成为新一轮平台工程化的重要组合，并指出安全隔离、测试策略与反馈类型需要与课程目标协同设计\cite{paiva2022automated}。Malmi 等早期关于大规模课程自动评测的经验研究也提示，当提交规模上升时，评测链路的稳定性与可运维性将与判题正确性同等重要\cite{malmi2002masscourses,saikkonen2001fully}。Luxton-Reilly 等对入门编程教学研究的综述虽不限于 OJ，但其中关于练习、反馈与迭代之间闭环的讨论，为理解在线评测在教学体系中的位置提供了更宏观的参照\cite{luxtonreilly2018introductory}。

除学术论文外，工程社区也沉淀了一批可复用的开源评测与编排组件，对本科毕设的系统选型具有直接参考价值。Judge0 提供了可部署的在线判题 API 与沙箱执行能力，适合作为判题执行服务化方向的参考实现\cite{judge0online}；DOMjudge 作为成熟竞赛评测系统在题目导入、判题调度与榜单机制等方面积累了大量实践经验\cite{domjudgeonline}。Kubernetes 与 Docker 的官方文档则分别提供了编排与容器打包的基础语义与最佳实践，可与高校信息化环境中的云原生基础设施方案相互对照\cite{kubernetesdocs,dockerdocs,huawei2020cloudnativedoc,hezhenwei2020kubernetes}。这些开源实现也从侧面印证了上文所述的主链路确定性叠加反馈分层的设计方向，可以作为本文系统选型与实现路线对比的工程参照。

\section{容器化执行与弹性支撑}

云原生是一种面向云环境的软件构建与运行理念，其核心关注点包括容器化封装、弹性扩展、自动编排、持续交付和可观测性。对于在线编程评测平台而言，云原生并不只是把系统部署到云服务器上，而是要求平台在设计阶段就考虑服务拆分、资源调度、运行隔离和故障恢复等问题\cite{burns2016borg,hezhenwei2020kubernetes}。

容器化技术为在线编程评测平台提供了统一、可复制和易于回收的运行环境。不同用户提交的程序可能依赖不同语言、编译器和运行库，如果直接在宿主机执行，不仅环境管理复杂，还会带来安全风险。通过将评测任务放入容器中执行，可以有效实现运行环境标准化，并借助资源限制、文件系统隔离和进程隔离等机制提高平台安全性。

在更高层面上，容器编排平台还可以对评测服务进行统一调度和弹性扩缩容。当提交任务短时间内集中到达时，平台可以按需扩展评测节点；当负载下降时，再回收多余资源，以降低运行成本。由此可见，容器化和云原生技术为在线编程评测平台提供的不只是部署方式，更是一套工程化支撑手段\cite{burns2016borg,balalaie2016microservices,difrancesco2019microservices,hezhenwei2020kubernetes}。

除容器编排外，无服务器计算也是近年来值得关注的云原生实现路径。Alemu 在程序作业自动评测场景下使用 API Gateway、SQS、Lambda 和 DynamoDB 等组件实现了无服务器方案，并从响应时间、成本和环境影响三个维度进行了评估，结果表明无服务器方案在突发场景下具备较好的按需扩展能力和空闲资源节约潜力\cite{alemu2023serverless}。这说明在线编程评测平台的云原生化并非只有容器集群这一种路线，事件驱动的按需执行同样具有参考价值。但对于需要较强编译环境控制和运行时资源限制的题目，如何在弹性与可控之间取得平衡，仍然是架构选型中的关键问题。

从工程实现角度看，容器技术之所以适合判题场景，关键在于它把不可信的用户代码与可信的平台服务之间的边界显式化：一方面通过镜像固化编译器与运行库版本，降低环境漂移；另一方面通过 cgroup/namespace 等机制提供资源与命名空间隔离，并结合默认关闭网络等策略降低横向渗透与滥用风险\cite{dockerdocs,opencontainers,nist201716800190}。Felter 等对传统虚拟机与 Linux 容器的性能对比研究表明，在部分工作负载下容器能够显著降低启动与调度开销，但也提示性能结论与负载形态强相关\cite{felter2015containers}。Bernstein 进一步从云计算演进角度概括了从 LXC 到 Docker 再到 Kubernetes 的技术脉络，为理解编排与声明式部署为何会成为云原生标配提供了背景\cite{bernstein2014containers}。在更强隔离诉求场景下，Agache 等提出的 Firecracker 通过面向 Serverless 的轻量虚拟化把接近容器的开销与接近虚拟机的边界结合起来，代表另一类可借鉴的工程路线\cite{agache2020firecracker}。图~\ref{fig:ch2-container-boundary}给出了本文讨论中常用的信任边界示意。

\section{服务解耦与异步调度}

\subsection{微服务拆分与任务队列}

微服务架构强调围绕业务能力对系统进行拆分，使各个服务能够独立开发、独立部署并通过标准接口协作。在在线编程评测平台中，用户管理、题库管理、代码提交、评测调度、结果展示和 AI 辅助反馈等功能本身就存在较明显的职责边界，因此具备服务化拆分的基础\cite{balalaie2016microservices,difrancesco2019microservices}。

评测任务调度在平台里是关键技术要点。判题时一般会有编译、执行、用例校验等耗费时间的操作，要是在请求线程中直接同步处理，容易造成响应阻塞还有资源争抢。平台采用提交入队、异步调度、工作节点执行、结果回传这种处理模式更合适。借助消息队列或者任务队列来缓冲提交的任务，能够提高系统削峰填谷的能力，还能让判题资源调度更清晰且可控。

在微服务跟任务调度相结合的模式当中，系统能够把面向用户的请求服务、面向判题的执行服务区分开来。前面的那种服务负责接收提交、管理状态、展示结果，后面的那种服务负责拉取任务、执行程序、返回判题信息。这样的模式既契合在线编程评测平台的业务特性，还为后续引入多语言支持、优先级调度、节点监控等功能奠定了不错的架构基础。

从软件架构表达方式看，微服务拆分、限界上下文与异步消息等模式已被大量工程实践总结为可复用的参考模型\cite{richardson2018microservices,newman2021buildingmicroservices,fowler2014microservices,difrancesco2019microservices}。对在线评测平台而言，这类方法的价值不在于把系统强行拆成许多仓库，而在于让提交受理、任务排队、判题执行、结果写回与观测审计等职责在演进过程中仍能保持清晰边界，从而降低联调成本与故障半径\cite{balalaie2016microservices}。

\subsection{事件驱动与实时状态回传}

在在线评测场景中，代码提交往往具有明显的突发性。如果仍采用请求到达后立即在同一链路中完成判题这种模式，容易出现阻塞、超时和资源竞争等问题。因此，更合适的做法是先在业务侧保存提交记录，再由独立工作节点异步执行判题流程。这样既能降低前端请求链路的阻塞风险，也更便于形成清晰的状态流转模型。

事件驱动机制的关键价值并不只是把任务放进队列那么简单，而在于使业务服务、调度服务和执行服务之间的职责进一步清晰化。业务服务负责生成提交记录、维护用户视角的状态和处理权限校验；调度层负责转发事件、缓冲峰值和触发重试；工作节点则专注于编译、运行和结果写回。对于在线编程评测平台而言，这种分工非常适合请求短、执行长、资源敏感这一类业务特征，也有利于后续扩展为多节点判题或优先级调度模式。

与异步调度相配套的，通常还需要引入实时反馈机制。当提交进入排队、编译或运行阶段时，如果前端只能通过频繁轮询获知最新状态，不仅会增加系统开销，也会削弱用户体验。因此，采用基于发布订阅或 WebSocket 的实时状态推送机制，可以在提交状态发生变化时主动把结果回传给页面，使用户及时看到排队中、编译中、运行中以及最终判题结果。这种异步执行配合实时回传的组合是现代在线编程评测平台提升交互体验和系统可扩展性的重要技术路径。WebSocket 协议为浏览器与服务器之间的全双工通信提供了标准化基础\cite{rfc6455websocket}；在具体实现中，还需要结合鉴权、心跳、重连与背压等机制，避免长连接在高并发场景下成为新的瓶颈\cite{owasp2021top10}。需要补充说明的是，除判题状态推送外，浏览器端语言服务客户端亦常通过 WebSocket 承载 LSP 的 JSON-RPC 会话，使编辑器能够在不刷新页面的前提下持续接收诊断与补全响应\cite{lsp2024spec,monacolanguageclientrepo}；这与异步判题配合实时 UI 在工程形态上同属长连接驱动的交互增强路线，但服务对象与后端进程不同，应在架构上显式区分。

\section{形成性反馈与教学支持}

传统在线编程评测平台的优势在于结果客观、流程标准化，但单纯返回 \texttt{AC}、\texttt{WA} 或 \texttt{CE} 等状态并不足以满足教学反馈需要。Ihantola 的研究指出，反馈形式本身会影响学生理解错误原因的效率\cite{ihantola2011automated}。这说明教学型平台的改进方向，不应只是继续提高判题吞吐量，还应关注反馈内容是否真正有助于学生继续修改代码。

Ihantola 的另一项结论是，某些自动评测能力更适合用于自学场景而非正式评分场景。例如，客户端执行的评测方式虽然便于学习材料迁移，但结果更容易被伪造，因此更适合练习而不是正式成绩评定\cite{ihantola2011automated}。这一点说明，同一平台中的自由练习、课程作业和正式考核，不一定应该使用完全相同的反馈和执行策略。

结合本文研究目标，可以把教学反馈理解为一个分层结构。底层是确定性的客观判题结果，用于保证评价一致性；中层是与编译错误、运行错误或输出差异相关的解释性信息，用于帮助学生定位问题；高层则是与代码结构、复杂度、风格和改进方向相关的形成性反馈，用于支持学习过程。本文在本科毕设范围内不追求实现完整的视觉反馈或学生自编测试评价体系，但会将 AI 辅助模块作为中层和高层反馈的主要实现路径，以提升传统 OJ 平台在教学场景中的可用性。

围绕反馈是否足够教学化这一问题的讨论，近年来综述研究给出了更细粒度的证据。Messer 等指出，大量自动评分工具的反馈仍主要停留在测试通过与失败层面，能够覆盖可维护性、可读性等维度的工具相对更少\cite{messer2024automated}；Paiva 等也强调，反馈类型与教师可理解的学习证据同样重要\cite{paiva2022automated}。Sarsa 等从工程角度讨论了通过缓存、静态分析与机器学习预测等步骤减少无谓测试执行、从而加速反馈回传的可能性，为既要快又要稳的评测平台提供了方法参考\cite{sarsa2022speedingukicer}。图~\ref{fig:ch2-feedback-stack}给出了本文在讨论反馈设计时常用的分层示意。

\section{AI 辅助分析与反馈约束}

大语言模型在代码理解、自然语言生成和上下文推理方面的能力，使其在程序设计教学场景中具备较强的辅助价值。已有研究表明，AI 模型可以根据题目、代码和错误信息生成解释、错误分析和优化建议，从而帮助学生更快理解问题所在\cite{keuning2018feedback,sarsa2022llm,jacobs2024feedback}。

但在将 AI 引入在线编程评测平台时，必须明确其边界。首先，AI 输出具有概率性，不同提示语和不同模型版本可能导致反馈内容变化，因此不宜将其作为最终评分或判题依据。其次，AI 容易给出看似合理但并不完全准确的解释，若缺乏约束可能误导学生。再次，在教学场景中还必须关注学术诚信问题，避免 AI 直接给出完整答案而削弱学生独立思考过程。Finnie-Ansley 等关于 Codex 的早期研究提示，代码生成模型在典型入门题目上可能达到甚至超过部分学生表现，这会直接冲击传统作业与考试形态\cite{finnieansley2022robots}；Denny 等关于 Copilot 提示工程的研究则说明，学生与模型之间的自然语言交互将成为新的能力维度\cite{denny2023conversing}；Kazemitabaar 等通过实验讨论了 AI 代码生成器对新手学习的影响，提示效率提升与依赖风险这两种现象可能并存\cite{kazemitabaar2023chi}。Raihan 等对 LLM 进入计算机教育的系统综述进一步从课程、学习支持与治理等角度总结了研究缺口\cite{raihan2025llmcsed}。

与直接让模型回答编程问题这种通用场景相比，面向课程平台的 AI 辅助系统更强调上下文约束和教师可管理性。Lubin 的硕士研究提出，学生侧 AI 助教若要真正服务个性化学习，应尽可能利用课程材料、作业说明和任务上下文生成有针对性的支持，同时为教师提供交互摘要与管理工具，以便教师了解学生求助模式并对 AI 使用边界进行治理\cite{lubin2025llm}。这一结论说明，教学平台中的 AI 并不只是一个孤立的问答接口，而应是与课程语境、任务目标和教师管理机制相协同的支持组件。

因此，本文将 AI 辅助模块定位为基于判题结果的学习支持组件。它的输入包括题目信息、提交代码、编译或运行错误信息以及测试结果摘要，输出内容则包括错误原因分析、关键知识点提示和不直接给出答案的优化建议。通过这种方式，平台既保持了传统判题机制的客观性，也补充了一定的解释性反馈\cite{jacobs2024feedback,wangfang2023ai,zhanghongzhuo2024genai,lubin2025llm}。在模型选择与评测方面，Koutcheme 等比较了开源与专有模型在生成反馈以及评判反馈质量这两类任务上的表现，为教学平台采用多模型与成本可控策略提供了实证参考\cite{koutcheme2024evaluatinglm,koutcheme2024openfeedbackiticse}；Pankiewicz 等在 RunCode 平台上开展的实验则显示，学生对 GPT 生成提示的有用性评价总体积极，但也提示需要关注提示依赖与评价口径\cite{pankiewicz2023icce}。

\section{浏览器端编辑器与语言服务器协议}

传统在线评测系统的前端往往以题面、文本框与提交按钮三件套为主，编辑器能力多停留在关键字着色或轻量格式化。对入门学习者而言，这种形态的最大短板并不在于缺少所谓的炫技功能，而在于\textbf{语义反馈不足}：许多错误在静态分析或编译前端即可定位，却要到提交后通过冗长编译输出才能发现，显著拉长迭代周期。近年来，随着 Monaco 等组件成熟以及 LSP 生态普及，在浏览器中复用接近本地 IDE 的补全、诊断与悬停提示成为可能\cite{monacoeditorrepo,lsp2024spec}。

从协议角度看，LSP 将语言理解能力从编辑器内核中剥离出来，以独立语言服务器进程承载索引、诊断与补全计算；编辑器侧仅负责展示与用户交互，并通过 JSON-RPC 与服务器通信\cite{lsp2024spec}。对 Web 应用而言，常见工程形态是在浏览器内使用语言客户端库，通过 WebSocket 将 JSON-RPC 会话桥接到后端或侧车容器中的语言服务器（例如 C/C++ 场景下的 Clangd）\cite{monacolanguageclientrepo}。这与判题沙箱并不矛盾：判题关注的是如何在受控环境中执行不可信程序并得到测试结果，语言服务关注的则是如何在只读或受限上下文中分析源码以提供编辑辅助，二者在信任模型、资源配额与网络策略上应分别设计。

从教学支持角度看，编辑器侧语义反馈属于图~\ref{fig:ch2-feedback-stack} 所示反馈分层中的诊断层能力：它不改变客观判题结论，但能把大量低级错误前移到提交之前，使学生把更多注意力放在算法与测试设计本身。需要强调的是，语言服务器诊断与编译器错误并不完全等价：前者更偏静态语义与工程化提示，后者以能否生成可执行文件为准；因此平台仍应保留判题主链路的编译与运行反馈，而不能用 LSP 诊断替代评测结果。二者在信任模型与资源配额上相互独立，具体连接关系见第五章图~\ref{fig:ch5-lsp-arch} 与判题实现小节的对应说明。

\section{本章小结}

本章介绍了本文后续设计与实现所依赖的几个关键技术，包括自动判题、容器化执行、异步调度、实时状态回传、AI 辅助分析以及浏览器端编辑器与 LSP 等内容，并补充综述了自动评分工具研究趋势、容器隔离边界、反馈分层模型以及代表性开源参考实现。这些材料共同构成了后续需求分析和总体设计的基础。
