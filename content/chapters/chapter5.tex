\chapter{系统详细设计与实现}

\section{实现概述}

结合当前项目实现情况，平台采用全栈 Web 应用方式组织前后端能力：前端负责题目展示、代码编辑、提交记录查看与 AI 反馈交互，后端负责题目读取、提交入库、判题调度、容器调用和分析结果持久化。系统虽然部署为统一工程，但在逻辑职责上仍按照“题库管理、判题执行、分析反馈、辅助管理”进行拆分，使后续模块迭代和论文叙事保持一致。

从已有实现来看，系统主链路已经覆盖题目列表、题目详情、代码编辑、代码提交、自动判题、提交详情和 AI 辅助反馈等核心功能，其中“判题结果先确定、AI 反馈后补充”的处理策略与本文前述总体设计相一致。对于教师管理、学生管理和复杂统计面板等配套页面，虽然工程中已存在部分实现，但本文不将其作为核心成果展开，而是将论文重点放在评测平台主链路的设计与实现上。

\subsection{用户与权限数据设计}

当前系统用户模型以 User 实体为核心，记录用户名称、邮箱、密码、头像和角色等信息。角色字段用于区分管理员、教师与普通学生等不同访问主体，并结合认证模块完成登录后的身份识别。对于平台主链路而言，角色机制主要影响题目维护权限和后台访问范围，而不改变学生提交判题的核心流程。

\subsection{题目内容与模板数据设计}

题目实体 Problem 负责描述 displayId、难度、是否发布、时间限制、内存限制等基础属性。其中 displayId 用于面向用户的题号展示，timeLimit 与 memoryLimit 则直接影响判题执行阶段的资源约束。ProblemLocalization 通过 problemId、locale 和 type 组合唯一确定一条本地化内容，用于分别存储题目标题、题面描述和题解内容；Template 则通过 problemId 与 language 的组合存储不同语言的模板代码。

从数据一致性角度看，当前模式设计并非简单地把所有文本和代码堆叠在同一张表中，而是通过复合主键和唯一约束保证多语言内容与模板代码的组织稳定性。例如，同一道题目在同一种语言下只能存在一份模板代码，同一道题目在同一种语言和同一种内容类型下也只能存在一份本地化文本。这种约束设计不仅减少了后台维护中的重复数据，也使前端在读取题目详情时能够以更确定的方式获取标题、题面、题解和模板代码。

Submission 是整个平台中最关键的业务实体之一，用于存储语言类型、源代码、判题状态、错误信息、时间使用量和内存使用量等信息。Testcase 与 TestcaseInput 共同描述标准测试数据；TestcaseResult 则用于保存每个用例执行后的结果。这样的结构使判题过程能够精细记录到“提交级”和“用例级”两个层面，便于展示提交详情，也便于后续统计和教学分析。

\section{题库管理模块实现}

\subsection{题库实体与职责划分}

题库管理模块主要由 Problem、ProblemLocalization、Template 和 Testcase 等实体支撑。其中 Problem 负责题目基础约束，ProblemLocalization 负责题目文字内容，Template 负责不同语言的模板代码，Testcase 及其输入项负责标准评测数据。这样的设计使题目内容维护、前端展示和后端判题能够围绕同一份题目数据协同工作。

从功能边界上看，题库管理模块的主要任务是为判题主链路提供准确、完整和可维护的数据来源，而不是在论文中展开复杂后台交互细节。因此，本文只描述与题目内容组织、模板代码和测试数据直接相关的实现。

系统同时支持按语言维度为题目保存模板代码，使学生进入题目页后可以直接获得对应语言的初始代码。测试数据则通过 Testcase 与 TestcaseInput 共同组织，其中 TestcaseInput 保存有序输入项，便于在运行阶段按顺序组合为标准输入流。

在题目内容组织方式上，系统将标题、题面描述和题解说明分别以 ProblemLocalization 的不同 type 存储，并配合 locale 字段支持中英文等多语言内容读取。当前实现中，题目读取动作会统一查询题目基本信息、模板代码、测试用例及其输入项、本地化内容等数据，并将题面描述序列化为可直接渲染的内容对象返回前端。

进一步来看，题目读取模块并不是把数据库内容原样透传给前端，而是先在服务端完成一次聚合与整理。系统会在单次查询中同时带出模板代码、测试用例及其输入项，以及符合当前语言环境的本地化文本；随后，再从本地化内容中分别提取标题、题面描述和题解字段，并将题面描述序列化为 MDX 数据结构。这样处理的好处在于，前端页面拿到的数据已经尽可能接近“可直接渲染”的形态，减少了页面层对原始数据库结构的了解负担，也使题目详情页、题解页和编辑器初始化逻辑能够围绕统一的数据接口协同工作。

从工程边界上看，当前实现对本地化内容采取了较为直接的读取策略，即按当前 locale 查询匹配内容，不在读取层额外引入复杂回退规则。这种处理方式实现简单、行为清晰，适合当前原型阶段；若后续面向更正式的多语言教学场景，还可以在服务端增加“当前语言缺失时回退到默认语言”的策略，以进一步提升题库内容的鲁棒性。

\subsection{提交受理与状态流转}

在提交入口处，系统首先校验用户是否登录、题目是否存在、测试用例是否存在以及对应语言的 Docker 配置是否完整。通过这些前置检查，可以避免无效请求直接进入判题流程。校验通过后，系统创建 Submission 记录，并以 Pending 状态作为判题起点。随后，源代码被封装为指定文件名写入 tar 数据流，再上传到新建的容器工作目录中，为后续编译执行做准备。

将 Submission 记录放在编译和运行之前创建，具有明确的工程价值。第一，它使系统能够从用户点击提交的那一刻起就拥有稳定的提交编号和状态载体，便于前端立即展示记录并等待后续状态更新；第二，它为 AI 分析、页面刷新和异常兜底提供了统一锚点，即使后续编译、运行或容器调用失败，系统也能把错误回写到同一条提交记录中；第三，这种“先建记录、再推进状态”的处理方式与未来的异步任务队列模型天然兼容，因为无论任务由当前请求线程直接执行，还是由后台 worker 异步执行，状态都可以围绕同一条 Submission 演进。

\subsection{编译流程实现}

编译阶段会先把 Submission 状态更新为编译中，再根据语言类型生成对应命令。当前实现中，C 语言通过 gcc -O2 编译为 main，C++ 通过 g++ -O2 编译为 main。为避免编译日志无限增长，系统对编译输出设置了长度限制；若编译失败，则将错误信息写回 Submission.message，并把状态更新为 Compilation Error。

编译输出长度限制是一个很有必要但容易被忽略的实现细节。若系统对编译器标准错误流完全不做限制，极端情况下用户程序可能产生非常长的错误日志，不仅会增加数据库写入压力，也会影响页面展示与网络传输效率。当前实现通过受限写入流截断编译输出，只保留限定长度内的错误信息。对于教学场景而言，这样的截断通常不会影响学生定位常见语法错误，却能有效降低异常提交对系统资源的消耗。

\subsection{运行与用例判定实现}

在运行阶段，系统按测试用例顺序逐个创建执行实例，将排序后的输入参数写入标准输入流，再根据程序输出与标准输出进行比较，从而判定答案是否正确。若题目配置启用了裁剪空白字符比较，则输出对比采用 trim 方式；否则按原始输出严格匹配。每个用例的输出、时间消耗和正确性结果都会保存到 TestcaseResult。

若某个测试用例触发答案错误、运行错误、时间超限或内存超限，系统会立即写入对应的 TestcaseResult 记录，并终止后续用例执行。只有当前一个用例返回正常执行状态时，才会继续处理下一个用例。这一实现符合在线评测系统常见的短路判题思路，也有助于节省执行资源。

当所有测试用例均通过后，系统会统计该提交下各用例的时间消耗，并结合容器运行统计更新最终的时间使用量和内存使用量，再把 Submission 的状态设置为 Accepted。这样，提交记录不仅保存了最终结果，还能保留一定的性能信息，为后续结果展示和教学分析提供依据。

在具体执行方式上，系统并不是简单地把所有输入一次性拼接后批量运行，而是围绕“按用例顺序逐个执行”的策略组织判题流程。每个测试用例对应的输入项会先按 \texttt{index} 字段排序，再拼接为标准输入流写入容器进程。这样做的直接好处是可以准确记录每个用例的输出和耗时，也便于在出现 \texttt{WA}、\texttt{RE} 或 \texttt{TLE} 时快速定位首个失败用例，而不必在混杂的整体输出中重新拆分结果。

此外，系统在全部测试用例通过后并不是简单取最后一个用例的耗时作为提交耗时，而是从所有 TestcaseResult 中提取非空时间并取最大值作为本次提交的时间摘要。这种处理方式更接近在线评测平台常见的“以最慢用例代表该次提交时间表现”的做法，也比简单求和更适合反映单次程序运行在最不利样例下的时间特征。内存使用量则通过容器统计信息提取峰值，为后续页面展示和性能分析提供摘要依据。

\subsection{资源约束与安全隔离实现}

容器创建逻辑中，系统为每次判题准备独立运行环境，设置工作目录、内存限制，并默认禁用网络，从而降低恶意代码或异常程序对宿主系统的影响。由于每次提交都在新的容器环境中完成编译和运行，平台可以较好保证不同提交之间的环境隔离和执行一致性。

这种执行方式虽然还属于单机原型阶段的轻量容器化判题，但已经体现出云原生思路中的几个关键点：统一镜像环境、按任务动态创建执行单元、资源限制和最小权限运行。对于毕设原型而言，这样的实现复杂度和可展示性之间取得了较好的平衡。

除运行时约束外，容器生命周期管理同样属于安全隔离的一部分。当前实现会在判题动作结束后无论成功还是失败都进入清理流程，尝试停止并删除对应容器，避免临时执行环境在宿主机上持续堆积。对在线评测平台而言，这种“单次提交对应单次执行环境、执行后立即回收”的策略虽然会带来一定容器启动开销，但能够换取更清晰的故障边界和更低的残留风险，尤其适合本科毕设原型阶段对稳定性与可说明性的要求。

\section{AI 辅助反馈模块实现}

\subsection{模块定位与触发方式}

AI 辅助反馈模块的作用并非替代评测，而是利用模型的代码理解和文本生成能力，为学生提供复杂度分析、质量评价和改进建议。该模块对应工程中的分析动作与详情展示逻辑，属于“后置辅助”能力，而不是主判题链路的一部分。

从具体使用方式上看，题目阅读、提交记录回顾、AI 问答和结果查看等信息密集型区域，在桌面端更适合并列呈现，以支持“边看题、边写码、边复盘”的并行操作；而在平板或手机端，更合理的策略是让核心编辑区域保持主要可见，同时将次级面板收纳为按需展开的区域。当前实现采用这种“核心内容常驻、辅助内容按需展开”的方式，能够在不重写整套业务逻辑的前提下，使同一工作区适配多类终端。对于程序设计课程而言，这种能力的实际意义并不在于鼓励学生长期用手机完成编码，而在于保证学生在课后、通勤或临时查看场景下，仍能顺畅访问题面、查看提交结果并进行轻量交互。

\subsection{多语言支持与主题一致性设计}

当前系统已经具备较明确的多语言支持基础。其一，在数据层面，题目标题、题面描述和题解说明通过 \texttt{ProblemLocalization} 以 \texttt{locale} 维度组织，前文已说明其可按语言读取不同内容版本；其二，在界面层面，平台提供独立的语言切换组件，并通过 Cookie 记录用户当前语言偏好，使页面文本、题目内容和部分交互提示能够围绕统一语言环境呈现。这样的实现不仅服务于中英文双语内容组织，也为后续扩展更多语种提供了稳定入口。

从论文主题与应用场景出发，多语言支持的价值不能仅理解为“页面上能切换中文和英文”这样一个局部功能点。对于程序设计教学平台而言，多语言能力至少带来三方面意义：第一，它使同一道题目可以围绕不同受众组织差异化表述，从而便于课程双语教学、术语对照和跨语言资源复用；第二，它为国际学生或中外合作教学场景预留了直接扩展空间，避免系统在初期设计时就被单一语言内容结构锁死；第三，它使 AI 问答、题解说明和平台提示可以在统一语言环境下协同工作，减少“题面是一种语言、界面是另一种语言、反馈又是第三种语言”所带来的理解割裂。

除语言外，当前前端还实现了深浅色主题切换，并将主题状态与代码编辑器风格保持联动。系统借助主题管理组件识别当前解析后的主题模式，在普通界面层切换明暗配色的同时，也为 Monaco 编辑器与差异对比编辑器选择对应主题，使页面容器、按钮、文本、代码高亮和 Diff 视图在视觉上保持一致。对编程类平台而言，这一细节非常重要，因为用户在同一工作区内会频繁在自然语言文本与代码文本之间切换；若主题不一致，极易产生视觉跳变和阅读疲劳。当前实现通过统一主题映射减少了这种不连续感，也使平台更适合长时间使用。

\subsection{编辑器工具栏与交互式 AI 辅助}

在代码编辑阶段，平台并未把 AI 能力仅局限于“提交后生成一段总评”，而是进一步把部分分析能力前置到编辑器工具栏中。当前工具栏除语言切换、撤销重做、格式化、复制等常规能力外，还包含语言服务连接状态提示、复杂度分析按钮、代码优化按钮以及原始代码与优化结果之间的视图切换按钮。这说明系统中的编辑器并非孤立文本框，而是一个围绕编程求解过程持续提供反馈的交互节点。

其中，复杂度分析按钮可以在用户正式提交前，直接基于当前编辑器中的代码请求 AI 返回时间复杂度与空间复杂度结果。这类能力的教学价值在于，它把“复杂度意识”从作业批改后的总结环节提前到了编码进行时。学生在完成初版实现后，可以先判断当前方案是否存在明显的复杂度劣势，再决定是否提交。相比只在最终判题后给出笼统建议，这种即时分析更贴近真实的编程训练过程。

代码优化按钮则体现了另一类更具对比价值的辅助方式。系统在接收到优化结果后，并不直接粗暴覆盖学生当前代码，而是先将优化版本单独保存，再通过差异视图开关在原始代码与优化代码之间切换显示。这样处理有两个明显优点：一方面，它保留了学生原始思路，避免 AI 输出直接吞没学习过程；另一方面，差异视图能够把修改点显式呈现出来，使学生更容易理解“为什么这里被改动”“哪些语句只是格式优化，哪些属于算法级调整”。对于教学平台而言，这种“先比较，再决定是否采纳”的方式要明显优于单纯返回一段替换后的代码文本。

\subsection{上下文感知的AI问答面板}

除前述“提交后分析”和“编辑中分析”外，当前平台还在题目工作区中提供了独立的 AI 问答面板。该面板并不是一个脱离场景的通用聊天框，而是会自动读取当前题目的本地化题面描述，并在用户提问时把当前编辑器中的代码内容一并作为上下文发送给模型。换言之，AI 在回答时不仅知道“用户正在做哪一道题”，也知道“用户当前写到了什么程度”。这种上下文感知能力使问答更容易围绕具体题目、具体代码和具体问题展开，而不是停留在抽象的通用建议层面。

从教学支持视角看，这种设计有助于把 AI 角色控制在“解释、提醒、引导”而非“直接替代完成”的范围内。学生可以围绕当前代码询问复杂度、边界情况、语法错误来源或改进方向，而系统仍然保留代码编辑与提交控制权在学生手中。相比完全脱离题目上下文的通用问答工具，当前方案更适合在线评测场景，因为它天然嵌入了题面、代码、提交与反馈这一完整问题空间之中。这样一来，平台的 AI 能力不再只是一个附加插件，而是与主工作区结构深度结合的学习支持组件。

\subsection{运行环境与部署实现}

在运行环境支持上，系统通过配置项区分本地 Docker 模式和远程 Docker 模式。若在本地模式下运行，平台直接通过宿主机 Docker 套接字管理容器；若在远程模式下运行，则根据协议、地址、端口和证书建立远程 Docker 连接。这样的设计使判题执行环境能够与 Web 服务解耦，也为后续将判题节点迁移到独立服务器或容器集群提供了可实施路径。

本轮已在本地环境中完成基础部署验证。首先，通过 \texttt{docker compose -f compose.local.yml up -d postgres} 启动数据库容器，用户终端结果显示 \texttt{postgres} 服务已进入 \texttt{healthy} 状态；随后执行 \texttt{bun install} 完成依赖安装并触发 Prisma Client 生成，执行 \texttt{bunx prisma migrate deploy} 成功应用现有 10 个数据库迁移，执行 \texttt{bunx prisma db seed} 完成种子数据初始化。在此基础上，项目进一步通过了 \texttt{bun run build} 生产构建校验，构建输出中可见 \path{/problemset}、\path{/problems/[problemId]}、\path{/dashboard} 以及后台管理相关核心路由均已成功参与构建。这说明系统在当前阶段已经具备从数据库准备、模式迁移、数据初始化到前端生产构建的完整本地运行基础。图~\ref{fig:local-dev-env}进一步给出了系统本地运行界面与开发终端状态的联合证据，可作为本地演示环境已正常工作的直观说明。

此外，部署配置中已经显式考虑了健康检查和远程 Docker 场景。主服务依赖数据库和语言服务健康后再启动，能够降低初始化阶段的偶发失败；而远程 Docker 模式下可通过协议、地址、端口和 TLS 证书路径切换判题执行位置，说明项目在设计上已经把“业务服务部署位置”和“判题执行位置”解耦开来。即使当前论文阶段主要在单机环境中完成演示，这一实现仍然能够为后续扩展到独立判题节点或云主机判题提供直接基础。

\section{扩展性验证与工程预留}

\subsection{异步判题链路的重构验证}

在当前主线实现中，平台已经完成了同步式代码提交、容器化编译运行和结果落库流程；为了进一步验证后续扩展到独立判题 worker 的可行性，本文还在重构验证阶段尝试了“提交入队—后台执行—状态推送”的异步判题链路。该方案在提交创建后不立即于请求链路内完成全部判题，而是先生成 Submission 记录，再通过事件驱动方式触发后台判题任务，由独立执行单元负责完成编译、运行和结果写回。这一重构验证说明，当前平台的业务模型已经具备进一步拆分为业务服务与判题服务的基础。

与同步方案相比，异步判题链路更强调过程状态的显式化。例如，提交在进入执行前可先处于 Pending 或 Queued 状态，随后流转到 Compiling、Running，最终达到 Accepted 或错误状态。这种设计既提高了前端展示的可解释性，也为任务队列、节点扩容和异常重试提供了更清晰的状态基础。由于这一链路已经在扩展性验证中完成了原型性重构，因此它不是纯粹停留在概念层面的设想，而是具有明确工程参考价值的后续升级方向。

\subsection{实时状态回传与多判题模式预留}

在扩展性验证方案中，平台进一步采用实时状态回传机制，在判题状态发生变化时主动通知前端更新显示。这样一来，用户在提交代码后可以及时看到“已受理、编译中、运行中、完成”等阶段，而无需频繁手动刷新页面。对于在线评测平台而言，这种机制不仅改善交互体验，也有助于在高延迟或高负载场景下减轻无效轮询带来的系统压力。

此外，扩展性验证还体现了更细粒度的判题模式建模思路。除一般的完整提交模式外，系统还预留了 sample、icpc、oi 等不同判题模式的区分空间，用于适配样例运行、传统 ACM/ICPC 风格评测和 OI 风格评测等不同教学或训练场景。配合 Judge、JudgeRun 等中间实体，平台能够把提交级结果与测试用例级结果进一步拆分记录，从而为课程化教学统计、竞赛化训练和错误分析提供更细的结构化数据基础。

\subsection{课程化教学能力的衔接基础}

虽然当前主线实现尚未把课程、作业和课程级运行环境配置完整纳入业务闭环，但从工程预留角度看，平台已经具备若干可衔接基础。首先，现有题库、提交、测试用例和分析结果等核心模型已经形成较稳定的主链路，可作为课程作业场景下 Assignment 与 Submission 关联的基础；其次，现有 Docker 配置与远程 Docker 支持说明平台已经具备按配置切换执行环境的能力，这为后续进一步细化到课程级或作业级配置提供了良好起点；再次，异步判题与实时回传的扩展验证也说明，平台在教学高峰期具备走向“课程组织 + 后台调度 + 实时反馈”一体化架构的工程可能性。

因此，从本文的成果边界来看，当前主线实现已经完成“题库—提交—判题—分析”的核心平台原型，而课程化教学组织和课程级运行环境配置则属于在此基础上可继续推进的下一阶段增强方向。将二者与现有主链路结合后，平台将更贴近真实高校程序设计课程的应用方式，也更能够体现题目所强调的“云原生与 AI 辅助的一体化在线编程评测平台”这一目标。

\section{本章小结}

从部署方式看，当前系统已经能够支持单机环境下的完整演示与运行，也为后续分离判题执行环境、引入更多语言镜像、扩展多节点调度以及衔接课程化教学场景预留了基础。对本科毕设而言，这种“先完成完整原型，再通过扩展性验证与设计论证保留工程升级空间”的处理方式更有利于保证成果可展示、论文可落地。
