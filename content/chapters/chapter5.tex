本系统如上图架构所示采用全栈开发的模式，前端部分使用 React 框架展示题目描述、题解、测试用例、提交记录和 AI 辅助反馈组件，组件库与样式部分采用 Tailwind 和 Shadcn/UI，通过 Zustand 进行状态管理，后端部分使用 Server Action 接收代码提交后，会先创建可追踪的提交记录，然后再通过 Inngest 调度容器完成代码编译与运行，同时 Vercel AI SDK 会对提交的代码进行分析并生成相应分数，这些内容最终都会写入到 Prisma 管理的数据库中，Prisma 还可以根据表结构生成 TypeScript 类型，不但可以提供开发过程中的类型安全，让前后端使用统一的接口类型，还能非常方便地实现在不同关系型数据库中的迁移。

在具体的判题服务上，本系统参考了 Judge0 与 DOMjudge 等开源项目的 API 接口与相关文档中提到的沙箱边界与运维经验\cite{judge0online,domjudgeonline}，将 Web 服务和判题服务单独部署，还支持本地编译代码和远程编译代码。本地编译时会通过宿主机套接字启动容器进行编译，远程编译时会按照配置里的协议、地址、端口、证书等配置与远程服务器中的 Docker 建立连接，同时系统本身也支持 Docker Compose 一键部署，避免出现环境不兼容的情况。

\subsection{提交受理与状态流转}

用户点击提交按钮之后，系统会先检查用户的登录状态、确认题目和测试用例是否存在，同时还要核对对应语言的 Docker 配置是不是完整，检查都没问题后，\path{src/app/actions/judge.ts} 会生成一条状态为 \texttt{QD} 的 Submission 记录，再把提交 id 通过事件 \texttt{submissions/create} 发送给 Inngest。到这一步 HTTP 请求就可以返回结果了，接下来的编译和运行都交给异步链路处理，另外，提交入口还会把当前界面使用的语言传给 AI 分析环节，这样反馈里的 \texttt{feedback} 字段就能和用户的语言环境保持统一。

先把 Submission 记录建好，再进入编译运行这一步，能保证用户每一次提交都能留下稳定的记录，前端页面也能立刻展示提交内容。之后不管是异步链路里出现编译出错、运行出错，还是容器调用出错，各类报错信息都会统一回写到这同一条记录里，状态会从 \texttt{QD}、\texttt{CP}、\texttt{RU} 一直更新到最终状态，方便后续排查问题和复盘。

系统同时维护两种状态，一种是提交级状态，另一种是判题轨迹状态：\texttt{Submission.status} 主要用来给前端展示和筛选，\texttt{Judge.status} 和 \texttt{JudgeRun.status} 则负责记下编译过程，还有每个测试用例的执行细节，这两部分会通过统一映射保持状态一致。状态发生变化的时候，会通过广播推送到 problem 频道和 submission 频道，前端监听到变化后就会刷新提交列表和详情页，做到异步执行过程里信息可以连续更新。

\subsection{编译流程实现}

编译阶段是由 \path{src/inngest/functions/process-submission.ts} 调用 \path{src/lib/judge-runtime.ts} 里封装好的运行时来完成的。调用的函数会先把 Submission 的状态改成“编译中”，之后再按照提交代码的语言类型生成对应的编译命令，本文里，C语言和C++分别会用 \texttt{gcc -O2} 和 \texttt{g++ -O2} 编译出可执行文件 \texttt{main}。若编译失败，错误信息写入 \texttt{Submission.message} 和 \texttt{Judge.compileOutput}，状态更新为 Compilation Error。编译器标准错误流被保存后，前端详情页将其渲染为 shell 片段，供学生查看语法或链接错误。

\subsection{运行与用例判定实现}

在程序运行的时候，\path{process-submission.ts} 会调用对应的运行逻辑，按照测试用例的顺序一个一个执行，把排好序的输入参数写到标准输入流里面，再拿程序输出跟标准输出做对比来判断结果对不对。要是题目打开了裁剪空白字符对比的功能，就会用 trim 方法做对比，不然就做完全严格的匹配，每一个测试用例的输入、输出、错误输出、运行消耗的时间还有当前状态，都会保存到 JudgeRun 里。

跟同步串行判题不一样，本文把容器准备、源码上传、编译、逐个测试用例执行还有容器清理，整理成了 Inngest 函数里的分阶段步骤，图~\ref{fig:ch5-submission-list} 就展示了这条链路的运行过程。只要有一个测试用例跑出了 \texttt{WA}、\texttt{RE}、\texttt{TLE} 或者 \texttt{MLE}，系统就会马上把当前的 JudgeRun 存到数据库里，停下后面测试用例的执行，必须得前一个用例通过了才会继续跑下一个，这种提前终止的短路判题办法，减少了没必要的计算，能更快给出失败的结果。

要是全部用例都通过，系统会把每个用例的运行耗时还有容器统计信息汇总起来，更新最终的时间以及内存数据，并且把 Submission 状态改成 Accepted，运行过程里，每个用例的输入会按照 \texttt{index} 排序之后拼接成标准输入，再送到容器里运行，输出内容和耗时会分开存下来，方便找到第一个出错的用例到底是哪一个。全部通过的时候，系统会从每个 JudgeRun 里挑出非零的时间，取里面最大的那个当成这次提交的最终时间数据，不会只拿最后一个用例的耗时来算；而内存使用量则是利用容器的统计信息提取出峰值，给页面展示还有性能分析提供相关数据。

\subsection{资源约束与安全隔离实现}

容器创建的逻辑里，系统会给每次判题准备单独的运行环境，设置好对应的工作目录还有内存限制，默认会把网络关掉，以此降低恶意代码或者异常程序影响宿主系统的可能。每次提交都会在新的容器环境里完成编译和运行，能保证不同提交之间环境隔离开，执行结果也一致。

判题结束之后，不管这次提交是成功还是失败，系统都会停止并且删掉对应的容器，避免临时的执行环境一直堆在宿主机上。这种一次提交对应一个执行环境、执行完马上回收资源的策略，虽然会带来一点容器启动的额外开销，但换来了更清晰的故障边界，也降低了程序残留带来的风险。

\subsection{判题异常路径、错误回写与可观测性}

除了编译失败、答案错误还有运行超时这些学生端常出现的问题之外，这套系统还得覆盖一类来自系统本身的异常情况，像是 Docker 守护进程没法用、缺少对应镜像、题目或者测试数据没配全、远程 Docker 连接失败这类问题。要是不在状态模型里把这类问题单独区分出来，很容易会被错当成 \texttt{CE} 或者 \texttt{WA}，会让学生搞不清，把环境出的问题当成算法本身的问题反复修改代码。

本文把一部分系统级的失败映射成了 \texttt{SE} 状态，还在 \texttt{Submission.message} 里写入了能看懂的错误概括，同时会保留已经生成的提交记录，让前端可以展示出“失败但能追踪”这样的状态。编译产生的输出、运行产生的输出还有错误信息，会分别放到提交消息、Judge 轨迹和 JudgeRun 记录里，不会把好几种诊断信息混到同一个字段里。

从可观测性的角度来说，判题的整个流程需要在日志里关联用户、题目、提交 id 还有容器 id。本文实现的方案已经把提交 id 贯穿在 \texttt{judge.ts}、Inngest 函数还有编译运行各个模块里，方便定位每个阶段出的问题。当前方案还没接入分布式追踪系统，不过在关键的异常分支里已经打印了结构化日志字段，可以方便判断问题到底是出在异步函数吞吐不够，还是单机 Docker 资源被耗尽了\cite{kubernetesdocs}。

\section{AI 辅助子系统的流式响应与上下文构造实现}

AI 辅助子系统独立于主判题链路，在代码提交和编辑两个时机为学生提供解释、提示和对话支持。本节按总体架构、模型抽象、流式响应、结构化落库、编辑期同步辅助、上下文构造、边界与兜底七个层次展开。其中流式响应采用 \texttt{SSE} 方案，使聊天面板能够逐字输出回复，这与第四章异步判题的状态推送同属长连接增量推送。

\subsection{子系统总体架构与三类入口}

本系统将所有 AI 调用汇聚到统一的模型抽象层，前端对应三个独立入口：提交后异步分析、编辑期同步辅助和上下文聊天。

提交后异步分析由 \path{src/app/actions/analyze-code.ts} 的 \texttt{analyzeCode} Server Action 提供，在提交记录创建后触发，结果持久化为 \texttt{CodeAnalysis} 记录。编辑期同步辅助由 \path{src/app/actions/analyze.ts} 和 \path{src/app/actions/ai-improve.ts} 中的相关 Server Action 提供，被工具栏按钮直接调用并以 JSON 形式同步返回。上下文聊天由 \path{src/app/api/chat/route.ts} 的 Route Handler 配合浏览器侧 \texttt{useChat} 钩子实现，是三个入口中唯一采用流式响应的\cite{aisdk2024docs,aisdkreact2024docs}。

图~\ref{fig:ch5-ai-arch} 展示了三者在用户感知上的差异：提交后分析表现为几秒后自动浮现评估卡片，编辑期辅助为按钮停止加载后弹出 Diff 视图，上下文聊天则需要字符实时浮现。这些差异源于后端 API 形态：前两者使用 \texttt{generateText} 一次性返回，第三者必须用 \texttt{streamText} 建立长连接。提交后分析虽然围绕同一个 \texttt{submissionId} 展开，但不参与 \texttt{AC}/\texttt{WA} 等状态裁决。

\subsection{模型抽象层与 OpenAI 兼容 Provider 接入}

本系统未硬编码具体厂商 SDK，而是通过 Vercel AI SDK 的 Provider 抽象统一访问远端模型\cite{aisdk2024docs}。\path{src/lib/ai.ts} 中的 \texttt{createOpenAICompatible} 读取环境变量 \texttt{AI\_API\_KEY}、\texttt{AI\_BASE\_URL}、\texttt{AI\_MODEL}，生成统一的 \texttt{model} 实例供各模块复用。

需要切换模型时，只需修改 \texttt{AI\_BASE\_URL} 和 \texttt{AI\_MODEL} 即可，因为主流模型服务商均提供与 OpenAI 兼容的 \texttt{/v1/chat/completions} 端点\cite{deepseek2024api}。本文实测使用 DeepSeek 服务。\texttt{API\_KEY} 通过 \texttt{getRequiredEnv} 从进程环境变量读取，缺失时直接报错，避免延后失败\cite{owasp2021top10}。在图~\ref{fig:ch5-ai-arch} 中，模型层对应中部的统一模型层，所有调用方仅依赖 \texttt{generateText}、\texttt{streamText}、\texttt{tool} 三个 SDK 顶层函数，与具体 Provider 解耦。

\subsection{基于 SSE 的聊天流式响应实现}\label{sec:ch5-ai-sse}

服务端入口位于 \path{src/app/api/chat/route.ts}，解析对话历史 \texttt{messages} 后加入系统提示词，调用 \texttt{streamText} 获取流式输出，再通过 \texttt{toDataStreamResponse} 封装返回。同时设置 \texttt{maxDuration = 30} 约束长连接的最长执行时间\cite{nextjsdocs}。

浏览器侧由 \path{src/features/problems/bot/components/form.tsx} 配合 \texttt{@ai-sdk/react} 的 \texttt{useChat} 钩子完成增量渲染，组件消费 \texttt{messages}、\texttt{input} 和 \texttt{handleSubmit} 等状态。新文本片段到达时，钩子更新消息列表，页面重新渲染，并通过 \texttt{MdxPreview} 展示为富文本。

\subsection{提交后异步分析与 Tool Calling 强约束}

提交后异步分析在 \path{src/app/actions/analyze-code.ts} 中实现，是 \texttt{CodeAnalysis} 表的唯一写入方。其难点不在于调用模型本身，而在于让概率性输出稳定落到关系型表的特定列上。

\texttt{analyzeCode} 进入函数后立即创建一条 \texttt{status="QUEUED"} 的 \texttt{CodeAnalysis} 记录，在 \texttt{try} 块内推进到 \texttt{PROCESSING}，调用模型，并在工具回调内完成 \texttt{COMPLETED} 写入，异常则被 \texttt{catch} 捕获并将状态置为 \texttt{FAILED}。分析任务由 Server Action 在提交受理后异步触发，只写入 \texttt{CodeAnalysis} 表，不阻塞判题事件。因此即使 AI 服务故障，学生仍可拿到 \texttt{AC}/\texttt{WA} 等结果，仅看不到分析卡片。

为避免模型以自由文本形式返回 JSON 再走正则解析，本实现采用 Vercel AI SDK 的 \texttt{tool} 与 \texttt{toolChoice} 联合机制\cite{aisdk2024docs}。在 \texttt{generateText} 调用中声明唯一一个名为 \texttt{saveCodeAnalysis} 的工具，其入参由 \texttt{zod} 描述为一组结构化字段，包括时间复杂度、空间复杂度、五项 0 至 100 整数分数与一段长文本反馈，回调函数直接以这些字段更新 \texttt{CodeAnalysis} 记录并将状态推进到 \texttt{COMPLETED}。同时通过 \texttt{toolChoice} 指定该工具为强制调用项，不允许模型产生自由文本。

\subsection{编辑期同步辅助：复杂度分析与代码优化}

编辑器工具栏的复杂度分析按钮与代码优化按钮分别由 \path{src/app/actions/analyze.ts} 中的 \texttt{analyzeComplexity} 和 \texttt{optimizeCode} 实现，二者均使用非流式 \texttt{generateText}，再进行 JSON 解析。

复杂度分析通过 \texttt{system} 提示词限定 \texttt{Complexity} 的八个枚举值（\texttt{O(1)}、\texttt{O(logN)}、\texttt{O(N)} 等），要求模型返回 \texttt{\{"time":"O(N)","space":"O(1)"\}} 格式，返回后用 \texttt{safeParse} 校验。这种提示词限定枚举、解析端校验的策略，确保最终字段属于预定义集合，避免 \texttt{O(N\textsuperscript{2})}、\texttt{Linear} 等不规范字符串导致渲染失败。

代码优化按钮的逻辑位于 \path{ai-improve.ts}。提示词包含当前代码、可选错误信息和题目描述，同时附带题目对应的语言模板代码。输出格式限定为 \texttt{\{optimizedCode, explanation, issuesFixed\}} 的 JSON。考虑到模型可能将结果包裹在 json 围栏中，实现先用正则提取代码块内的 JSON，提取不到则回退到全文第一个花括号内容，最后通过 \texttt{safeParse} 执行校验。

优化结果返回前端后存入 \texttt{useProblemEditorStore} 的 \texttt{optimizedCode} 字段，不会直接覆盖原代码，允许学生在普通编辑器与 Diff 编辑器之间切换查看改动。

\subsection{聊天面板的上下文构造与题面注入}

聊天面板初始化时放入一条 \texttt{role: "system"} 的题面消息，每次提交时将当前编辑器代码用 Markdown 围栏包装为另一条 \texttt{role: "system"} 消息，追加到对话末尾后触发请求。

题面在用户进入页面时即固定，作为初始系统消息可避免重复传输；代码会被频繁修改，每次提问时拼入当前代码，保证模型看到的是用户此刻的版本。

题面与代码使用 \texttt{system} 消息而非 \texttt{user} 消息，是因为 OpenAI 协议中 \texttt{system} 消息的语义是模型应将其作为既定背景理解，与用户提问相分离\cite{deepseek2024api}，避免模型把题面和代码反复抄回给回答。结合要求以用户当前语言回复的提示词，模型既能知晓题目与代码，又能用用户熟悉的语言给出简洁回答。

\subsection{故障兜底与教学边界}

AI 子系统的失败兜底分为三层：第一，所有 AI 调用以 Server Action 或独立 Route Handler 形式存在，其结果不参与 \texttt{Submission.status} 的状态裁决，即使模型不可达或返回格式错误，学生仍能获得标准的 \texttt{AC}/\texttt{WA} 等结果。第二，\texttt{analyze-code.ts} 中所有 zod 字段均为 \texttt{optional}，模型返回缺少某些维度时，仅部分字段为空，前端显示占位即可。第三，所有失败分支将状态写为 \texttt{FAILED} 并保留时间戳，配合日志可定位问题阶段。

教学边界方面，第三章与第四章已阐明 AI 可控性与“解释不裁决”的定位；本实现通过独立 Route Handler 与 Server Action 承载 AI 调用、\texttt{CodeAnalysis} 与 \texttt{Submission.status} 分离写入、以及优化结果不覆盖编辑器原文等方式落实上述约束。

\subsection{Monaco 编辑器与基于 LSP 的 IDE 级语言服务}

本节会结合具体实现代码，来说明编辑器功能与语言服务链路的实际落地方式，重点聚焦那些和编码体验直接相关的关键模块。

许多传统在线评测系统仍采用轻量文本框或简化编辑器，常见功能止步于关键字着色与基础缩进。对入门学生而言，这类编辑器在拼写错误、漏写分号、括号不匹配、类型不匹配等高频问题上缺乏即时反馈，学生往往只能依赖编译器输出的大量信息自行定位，在题目规模变大或模板宏较多时，这种反馈链路会显著拉长试错周期。工程实现策略是将浏览器端编辑体验尽量对齐本地 IDE：以微软 Monaco Editor 作为代码编辑内核\cite{monacoeditorrepo}，并通过 Language Server Protocol 即 LSP 与独立的 C/C++ 语言服务器通信，使补全、诊断、悬停提示、签名帮助等功能以标准化方式进入 Web 工作区\cite{lsp2024spec,monacolanguageclientrepo}。

\noindent 前端依赖与编辑器基础能力。题目求解页的实现栈以 \texttt{@monaco-editor/react} 与 \texttt{monaco-editor} 为核心，并配合 \texttt{monaco-languageclient}、\texttt{vscode-languageclient} 与 \texttt{vscode-ws-jsonrpc} 将 LSP 的 JSON-RPC 消息映射到浏览器 \texttt{WebSocket} 传输层\cite{monacolanguageclientrepo}。编辑器默认选项在 \path{src/config/editor.ts} 中集中配置，启用 ligatures、括号配对着色、缩进参考线、粘性滚动、平滑滚动与自动换行等特性，使长时间读码与改码的视觉负担更低。主题方面，工程使用 Shiki 高亮器并通过 \texttt{@shikijs/monaco} 将配色注册到 Monaco，从而使代码区与站点深浅色主题保持一致，与图~\ref{fig:dark-theme-workspace} 所示工作区观感一致。

\noindent 语言服务端点注入与连接建立。语言服务的连接参数并不写死在前端常量中，而是由服务端在渲染题目页时从数据库读取并注入。具体而言，\path{src/features/problems/code/components/content.tsx} 在服务端执行 \texttt{prisma.languageServerConfig.findMany()}，将返回的 \texttt{LanguageServerConfig} 列表传入 \texttt{ProblemEditor}，再下发到 \texttt{CoreEditor}\cite{prismadocs}。数据模型在 \texttt{schema.prisma} 中以语言为主键记录 \texttt{protocol}、\texttt{hostname}、\texttt{port} 与 \texttt{path} 等字段，使同一套前端代码可以在本地 Compose、内网部署或公网域名等不同环境下复用，只需调整种子数据或数据库配置即可。

在浏览器侧，\path{src/components/core-editor.tsx} 根据当前语言选择匹配的 \texttt{LanguageServerConfig}，拼接出 \texttt{WebSocket} URL 并建立连接，连接建立后创建 \texttt{MonacoLanguageClient} 并启动，使 Monaco 与语言服务器进入同一套 LSP 会话。编辑器挂载完成后才发起连接，卸载时停止 client，避免页面切换造成资源泄漏。工具栏中的 \texttt{LSP} 状态指示组件 \path{lsp-connection-indicator.tsx} 通过观察 \texttt{WebSocket} 的就绪状态给出可视化反馈，让学生明确当前是否具备语言级诊断能力，这与仅依赖提交后判题反馈的体验有本质差异。

\noindent 容器化语言服务与 Compose 编排。语言服务器本身同样以容器方式运行，便于与主服务生命周期对齐。工程 \texttt{compose} 配置中除 \texttt{judge4c} 与 \texttt{postgres} 外，还包含 \texttt{lsp-c} 与 \texttt{lsp-cpp} 两个服务镜像。二者基于 \path{docker/lsp/clangd} 构建，在容器内通过 \texttt{jsonrpc-ws-proxy} 将 \texttt{WebSocket} JSON-RPC 转发到 \texttt{clangd} 进程，\texttt{servers.yml} 中声明 \texttt{/usr/bin/clangd} 及后台索引参数。主服务通过 \texttt{depends\_on} 等待语言服务健康检查通过后再启动，从而降低页面已打开但语言服务尚未就绪的偶发体验问题。该编排方式也与前文所述判题执行与辅助能力尽量容器化、可替换的总体思路一致\cite{dockerdocs,kubernetesdocs}。

\subsection{运行环境与本地部署}

平台采用多容器编排：\texttt{judge4c} 主服务承载页面访问、业务处理与判题入口，\texttt{postgres} 承担业务数据持久化，\texttt{redis} 作为 Inngest 与 Soketi 的共享基础设施，\texttt{inngest} 负责事件函数编排，\texttt{soketi} 负责判题状态实时推送，\texttt{lsp-c}/\texttt{lsp-cpp} 为 C/C++ 编辑器提供语言服务。主服务通过 \texttt{depends\_on} 等待数据库、Redis、Inngest 与语言服务健康检查通过后再启动，降低初始化阶段的偶发失败。当前镜像基础层采用 \texttt{node:22-bookworm-slim}，并安装 \texttt{openssl}、\texttt{ca-certificates} 与 \texttt{curl}，以满足 Prisma/OpenSSL 运行依赖和容器健康检查需要。判题执行位置由配置项区分为本地 Docker 与远程 Docker 两种模式：本地模式直接经宿主机 Docker 套接字管理容器，远程模式则按协议、地址、端口与 TLS 证书建立连接，从而把业务服务部署位置与判题执行位置解耦，为判题节点上云提供直接基础。
