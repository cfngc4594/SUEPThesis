\chapter{在线编程评测平台核心实现}

结合项目实现情况，平台采用全栈 Web 应用方式组织前后端能力：前端负责题目展示、代码编辑、提交记录查看与 AI 反馈交互，后端负责题目读取、提交入库、判题调度、容器调用和分析结果持久化。虽然项目部署为统一工程，但在代码职责上已经形成了相对清晰的模块划分。本章重点说明与论文主题最直接相关的核心实现，即题目读取、代码提交、容器化判题、AI 辅助分析以及前端工作区；教师管理、学生管理和统计分析相关页面虽已实现，这里仅在与主链路密切相关处进行说明。

本章结合当前工程实现，对平台核心模块进行分层说明，主要对应数据模型、题库组织、提交流转、容器化判题、AI 分析和前端工作区等部分。这样安排的目的，是让论文中的描述能够和实际代码结构较好对应起来。

在数据库访问层面，系统通过 Prisma 管理数据模型和查询逻辑，并在项目初始化或模式调整后通过生成客户端保持类型安全。题目、提交、测试结果和分析结果均通过统一的数据访问层进行读写，这使得前端页面、判题流程和 AI 模块之间能够围绕统一模型协同工作。

在运行环境支持上，系统通过配置项区分本地 Docker 模式和远程 Docker 模式。当在本地模式下运行时，平台会借助宿主机 Docker 套接字来管理容器，而在远程模式下运行时，会依据协议、地址、端口、证书来建立远程 Docker 连接。如此设计，使得判题执行环境能够同 Web 服务实现解耦，同时也支持将判题节点部署到独立服务器或者容器集群。

从工程生态角度看，本文实现所依赖的关键第三方组件均具有公开可查的文档或源码：容器与镜像语义可参考 Docker 与 OCI 规范\cite{dockerdocs,opencontainers}；编排与云侧扩展路径可参考 Kubernetes 文档与云原生参考材料\cite{kubernetesdocs,huawei2020cloudnativedoc}；关系型数据持久化遵循 PostgreSQL 官方手册所描述的事务与 SQL 语义\cite{postgresqlmanual}；对象关系映射与迁移工具链遵循 Prisma 官方文档\cite{prismadocs}；前端工程栈与路由构建可参考 Next.js 文档\cite{nextjsdocs}。在判题执行服务化方面，Judge0 与 DOMjudge 等开源社区实现提供了可对照的 API 形态、沙箱边界与运维经验\cite{judge0online,domjudgeonline}，有助于解释本文为何采用 Web 服务与独立判题执行环境分离的解耦思路，而不是把所有判题逻辑耦合在 Web 进程内。

\section{身份认证与会话管理实现}

平台采用 \textbf{Auth.js} 在 Next.js App Router 下完成身份认证，其 npm 包名为 \texttt{next-auth}，工程依赖为 5.x 预发布版本\cite{authjsdocs,nextjsdocs}。Auth.js 通过 \path{src/lib/auth.ts} 导出 \texttt{auth}、\texttt{handlers}、\texttt{signIn} 与 \texttt{signOut}；其中 \texttt{handlers} 由 \path{src/app/api/auth/[...nextauth]/route.ts} 以 \texttt{GET}/\texttt{POST} 形式挂载到 \texttt{/api/auth/*}，从而承接 OAuth 回调与框架内部的会话读写\cite{authjsdocs}。持久化适配器为 \texttt{PrismaAdapter}，用户、账户与会话等记录写入 PostgreSQL，与业务表共享同一数据库\cite{prismadocs}。

\subsection{认证提供方与登录入口页面}

\path{src/lib/auth.ts} 中注册的 \texttt{providers} 包括 \texttt{Credentials}、\texttt{GitHub} 和 \texttt{Google} 三类。\texttt{Credentials} 用于邮箱密码登录，\texttt{authorize} 回调内使用 \texttt{zod} 定义的 \texttt{authSchema} 解析入参，以 \texttt{Prisma} 按邮箱查询用户并以 \texttt{bcrypt.compare} 校验口令散列，校验失败时返回 \texttt{null}。\texttt{GitHub} 启用 \texttt{allowDangerousEmailAccountLinking} 以便与已有邮箱账户做提供方关联，相关风险控制遵循 Auth.js 文档建议\cite{authjsdocs}。\texttt{Google} 的配置方式与 GitHub 同属 OAuth 提供方，登录页同样渲染为第三方按钮；下文以 GitHub 为主描述 OAuth 主流程，Google 与之同构。

自定义登录页路径为 \texttt{pages.signIn = "/sign-in"}，对应 \path{src/app/(auth)/sign-in/page.tsx}。该页面上方为 \texttt{CredentialsSignInForm}，实现位于 \path{src/components/credentials-sign-in-form.tsx}；下方为分隔线后遍历 \texttt{providerMap} 生成的 OAuth 按钮表单。\texttt{providerMap} 由 \texttt{providers} 派生并\textbf{过滤掉} \texttt{credentials}，避免与上方表单重复\cite{authjsdocs}。注册流程由 \path{src/app/actions/auth.ts} 中的 \texttt{signUpWithCredentials} 完成：校验邮箱未被占用后，以 \texttt{bcrypt.hash} 的 10 轮加盐策略写入密码散列并创建用户；若当前为全库首位用户，则将角色更新为管理员，这与 \texttt{createUser} 事件中将首位用户赋予 \texttt{ADMIN} 角色的逻辑一致。该登录页的 UI 形态见图~\ref{fig:ch5-signin}。

\subsection{邮箱凭据登录与数据库会话}

凭据登录在 UI 层并非直接由浏览器调用 \texttt{/api/auth/callback/credentials}，而是先进入 Server Action \texttt{signInWithCredentials}：再次完成 \texttt{zod} 校验、数据库查询与 \texttt{bcrypt} 比对后，调用 \texttt{signIn("credentials", \{ redirect: false \})} 交由 Auth.js 建立会话\cite{authjsdocs}。成功后在客户端以 \texttt{toast} 提示并 \texttt{router.push(callbackUrl || "/")}。

Auth.js 配置中，\texttt{callbacks.jwt} 在检测到 \texttt{account.provider === "credentials"} 时为 \texttt{token} 打上 \texttt{credentials} 标记；随后在 \texttt{jwt.encode} 的自定义实现里，若 \texttt{token.credentials} 为真，则不再走默认 JWT 字符串编码，而是调用工程内的 \texttt{createSession}：生成 UUID 形式的 \texttt{sessionToken}，通过 \texttt{PrismaAdapter.createSession} 写入数据库，并把过期时间设为常量 \texttt{SESSION\_EXPIRY\_MS}，即 30 天。该返回值作为 Cookie 载荷由框架写入，从而使\textbf{凭据登录路径下的会话以数据库会话为主}，便于与 \texttt{PrismaAdapter} 其余表结构统一审计\cite{authjsdocs,prismadocs}。

\subsection{GitHub OAuth 登录与受保护业务的衔接}

用户点击 GitHub 按钮时，登录页内联 Server Action 调用 \texttt{signIn("github", \{ redirectTo: callbackUrl \})}。浏览器随后跳转至 GitHub 授权端点，用户在 GitHub 站点完成授权确认后回调本站的 \texttt{/api/auth/callback/github}，最终仍由 \texttt{handlers} 统一处理，流程见图~\ref{fig:ch5-oauth}。与凭据分支不同，OAuth 成功后的 \texttt{jwt.encode} 走 \texttt{next-auth/jwt} 的默认 \texttt{encode}，即\textbf{不进入}上述 \texttt{createSession} 分支；账户绑定与 \texttt{linkAccount} 等事件在 \texttt{events} 钩子中记录结构化日志，便于排查账号合并问题\cite{authjsdocs}。

无论从哪条分支登录，业务侧在服务端均通过统一的 \texttt{await auth()} 读取会话（例如 \path{src/app/actions/judge.ts}、\path{src/app/(protected)/dashboard/layout.tsx} 等）。判题入口据此取得 \texttt{session.user.id}，再写入 \texttt{Submission} 的外键，从而保证提交归属与认证身份一致；同时受保护页面在 layout 层就完成会话校验，未登录用户会被框架重定向到自定义登录页 \texttt{/sign-in}，避免在每个页面或 Server Action 中重复判空。安全方面，OAuth 客户端 ID、Secret 与回调 URL 等敏感配置项均通过 \texttt{getRequiredEnv} 从环境变量读取，缺失即抛错，避免凭据进入版本库或在生产期才暴露问题\cite{owasp2021top10}。两条登录分支的完整时序对比可见图~\ref{fig:ch5-auth-overview}。

  \caption{核心数据表实体关系示意}

当前系统用户模型以 User 实体为核心，记录用户名称、邮箱、密码、头像和角色等信息。角色字段用于区分管理员、教师与普通学生等不同访问主体，并结合认证模块完成登录后的身份识别。对于平台主链路而言，角色机制主要影响题目维护权限和后台访问范围，而不改变学生提交判题的核心流程。

\subsection{题目内容与模板数据设计}

题目实体 Problem 负责描述 displayId、难度、是否发布、时间限制、内存限制等基础属性。其中 displayId 用于面向用户的题号展示，timeLimit 与 memoryLimit 则直接影响判题执行阶段的资源约束。ProblemLocalization 通过 problemId、locale 和 type 组合唯一确定一条本地化内容，用于分别存储题目标题、题面描述和题解内容；Template 则通过 problemId 与 language 的组合存储不同语言的模板代码。

从数据一致性角度看，当前模式设计并不是把所有文本和代码都堆在同一张表中，而是通过复合主键和唯一约束保证多语言内容与模板代码的组织稳定性。例如，同一道题目在同一种语言下只能存在一份模板代码，同一道题目在同一种语言和同一种内容类型下也只能存在一份本地化文本。这种设计既减少了重复数据，也让前端读取题目详情时更容易获得确定结果。

\subsection{提交、判题轨迹与分析结果设计}

围绕提交流转主链路，平台还需要为每一次代码提交记录其判题状态、逐用例执行轨迹与 AI 辅助分析结果。本小节先以表的形式汇总各核心数据表的字段设计，再结合表中字段说明 \texttt{Submission} 状态码的取值含义，以及围绕这些表所设置的关键数据约束，最后回到提交、判题轨迹与分析结果三者之间的协作关系上展开说明。

Submission 作为整个平台非常关键的业务实体之一，能够用来存储诸多信息，诸如语言类型、源代码、判题状态、错误信息、时间使用量、内存使用量等内容。Testcase 与 TestcaseInput 一同对标准测试数据加以描述，而 Judge 与 JudgeRun 分别用于保存提交级判题轨迹和用例级执行结果。如此结构使得判题过程可以精细记录到提交级与用例级这两个层面，既有利于展示提交详情，也有助于统计与教学分析。

本文将判题数据拆分为 Submission、Judge、JudgeRun 三层。这样设计的直接好处是，提交级状态与用例级细节能够解耦，便于在列表页展示摘要并在详情页展示失败用例上下文。编译输出、运行输入输出和错误输出等诊断信息也能按职责归位，减少同一字段承担多种语义。

CodeAnalysis 用于保存 AI 辅助分析结果，它通过 submissionId 与 Submission 建立一对一关系，并使用独立状态字段跟踪分析任务的处理阶段。这样一来，AI 分析既可以异步运行而不阻塞主判题流程，也可以与客观判题结果保持分离存储。

ProblemLocalization & \texttt{problemId + locale + type} 复合主键 & 保证同一道题目的同一种内容类型在同一种语言下只有唯一版本，避免题面与题解文本冲突。 \\
Template & \texttt{problemId + language} 复合主键 & 保证每道题在每种语言下只有一份模板代码，便于前端切换语言时直接加载对应初始代码。 \\
CodeAnalysis & \texttt{submissionId} 唯一约束 & 保证一次提交只对应一条主分析记录，避免多次分析结果互相覆盖或重复展示。 \\
外键级联删除 & 多个实体对 Problem、Submission 的级联关系 & 当题目或提交被删除时，相关本地化文本、模板、判题轨迹和分析记录可自动清理，减少孤儿数据。 \\
提交与用例分层记录 & Submission、Judge、JudgeRun 分层设计 & 既保存提交级摘要，又保留用例级细节，为详情展示、错误复盘和统计提供更细粒度的数据基础。 \\

\end{longtable}

\section{题库与题目组织}

题库管理模块主要由 Problem、ProblemLocalization、Template 和 Testcase 等实体支撑。其中 Problem 负责题目基础约束，ProblemLocalization 负责题目文字内容，Template 负责不同语言的模板代码，Testcase 及其输入项负责标准评测数据。这样的设计使题目内容维护、前端展示和后端判题能够围绕同一份题目数据协同工作。

从功能边界上看，题库管理模块的主要任务是为判题主链路提供准确、完整和可维护的数据来源，而不是在论文中展开复杂后台交互细节。因此，本文只描述与题目内容组织、模板代码和测试数据直接相关的实现。

系统同时支持按语言维度为题目保存模板代码，使学生进入题目页后可以直接获得对应语言的初始代码。测试数据则通过 Testcase 与 TestcaseInput 共同组织，其中 TestcaseInput 保存有序输入项，便于在运行阶段按顺序组合为标准输入流。

在题目内容组织方式上，系统将标题、题面描述和题解说明分别以 ProblemLocalization 的不同 type 存储，并配合 locale 字段支持中英文等多语言内容读取。题目读取时会统一查询题目基本信息、模板代码、测试用例及其输入项、本地化内容等数据，并将题面描述序列化为可直接渲染的内容对象返回前端。

题目读取模块并不是把数据库内容直接透传给前端，而是先在服务端完成一次聚合和整理。系统会在单次查询中同时带出模板代码、测试用例及其输入项，以及符合当前语言环境的本地化文本；随后再提取标题、题面描述和题解字段，并将题面描述序列化为 MDX 数据结构。这样处理后，前端拿到的数据已经更接近可直接渲染的形态，页面层不需要过多了解底层表结构。

本文对本地化内容采用了较直接的读取策略，即按当前 locale 查询匹配内容，不在读取层额外引入复杂回退规则。这样处理实现简单、行为清楚，适合原型阶段；若面向更正式的多语言教学场景，可在服务端补充当前语言缺失时回退到默认语言的策略。

\subsection{提交受理与状态流转}

在提交入口处，系统会校验用户是否登录、题目是否存在、测试用例是否存在以及对应语言的 Docker 配置是否完整。通过这些前置检查，可以避免无效请求直接进入判题流程。校验通过后，\path{src/app/actions/judge.ts} 会创建状态为 \texttt{QD} 的 Submission 记录，并以 \texttt{name="submissions/create"} 的事件将提交 id 投递给 Inngest。这样，HTTP 请求在受理阶段即可快速返回，耗时编译与运行由异步执行链路继续推进。

将 Submission 记录放在编译和运行之前创建，具有比较明确的工程意义。这样做后，系统从用户点击提交开始就有了稳定的状态载体，前端可以立即展示记录，即使编译、运行或容器调用失败，也能把错误统一回写到同一条记录中。该实现中，这一载体还承担了异步链路中的状态锚点角色：\texttt{QD}、\texttt{CP}、\texttt{RU} 到终态由同一条记录持续流转，便于追踪与复盘。

在状态联动上，系统同时维护提交级状态与判题轨迹状态。\texttt{Submission.status} 负责前端高频展示与筛选，\texttt{Judge.status} 和 \texttt{JudgeRun.status} 负责编译与逐用例执行细节。两者通过统一映射规则保持一致，避免页面状态与轨迹状态错位。围绕这一映射，状态广播会同步推送到 problem 频道与 submission 频道，前端监听后触发刷新，使提交列表与详情页都能在异步执行期间连续更新。

\subsection{编译流程实现}

编译阶段由 \path{src/inngest/functions/process-submission.ts} 调度 \path{src/app/actions/compile.ts} 执行。函数会先把 Submission 状态更新为编译中，再根据语言类型生成对应命令。本文实现中，C 语言通过 gcc -O2 编译为 main，C++ 通过 g++ -O2 编译为 main。为避免编译日志无限增长，系统对编译输出设置了长度限制；若编译失败，则将错误信息写回 Submission.message，并同步写入 Judge 的 \texttt{compileOutput} 字段，同时把状态更新为 Compilation Error。

编译输出长度限制是一个容易被忽略但实际很有必要的细节。若对编译器标准错误流完全不做限制，极端情况下可能产生非常长的错误日志，不仅增加数据库写入压力，也会影响页面展示和网络传输效率。本文通过受限写入流截断编译输出，只保留限定长度内的错误信息。对于教学场景而言，这样的处理通常不会影响学生定位常见语法错误。

\subsection{运行与用例判定实现}

在运行阶段，\path{src/inngest/functions/process-submission.ts} 会在编译成功后继续调用 \path{src/lib/judge-runtime.ts} 中的运行逻辑。系统按照测试用例顺序逐个执行，把经过排序的输入参数写入标准输入流，再依据程序输出和标准输出对比判断结果。要是题目配置启用了裁剪空白字符比较，那么输出对比会采用 trim 方式，要是没有启用，就会按照原始输出进行严格匹配。每个用例的输入、输出、错误输出、时间消耗和状态都会被保存到 JudgeRun 里面。

与同步串行判题不同，本文将容器准备、源码上传、编译、逐用例执行和容器清理组织为 Inngest 函数内的阶段化步骤。图~\ref{fig:ch5-submission-list} 展示了该链路在运行面板中的阶段轨迹，可直接看到 \texttt{parse-event}、\texttt{load-submission}、\texttt{prepare-container}、\texttt{compile-submission}、\texttt{run-testcase} 与 \texttt{cleanup-container} 等步骤。这样既能在运行时日志中看到清晰的阶段边界，也能在异常时快速定位故障发生位置。对论文展示而言，该判题链路不是单函数黑盒，而是具备可追踪、可回放的执行轨迹。

若某个测试用例触发答案错误、运行错误、时间超限或内存超限，系统会立即写入对应的 JudgeRun 记录，并终止后面的用例执行。只有当前一个用例返回正常执行状态时，才会继续处理下一个用例。这一实现符合在线评测系统常见的短路判题思路，也有助于节省执行资源。

当所有测试用例均通过后，系统会统计该提交下各用例的时间消耗，并结合容器运行统计更新最终的时间使用量和内存使用量，再把 Submission 的状态设置为 Accepted。这样，提交记录不仅保存了最终结果，还能保留一定的性能信息，为结果展示和教学分析提供依据。

在具体执行方式上，系统并不是把所有输入一次性拼接后批量运行，而是按测试用例顺序逐个执行。每个测试用例对应的输入项会先按 \texttt{index} 字段排序，再拼接为标准输入流写入容器进程。这样可以更准确地记录每个用例的输出和耗时，也便于在出现 \texttt{WA}、\texttt{RE} 或 \texttt{TLE} 时快速定位首个失败用例。

当全部测试用例均通过时，系统会从各个 JudgeRun 里提取非空时间，并且选取其中最大值当作本次提交的时间摘要，而非仅仅取最后一个用例的耗时。这种做法更贴近在线编程评测平台常见的统计模式。内存使用量是借助容器统计信息提取峰值，从而为页面展示和性能分析提供摘要依据。

\subsection{资源约束与安全隔离实现}

容器创建逻辑中，系统为每次判题准备独立运行环境，设置工作目录、内存限制，并默认禁用网络，从而降低恶意代码或异常程序对宿主系统的影响。由于每次提交都在新的容器环境中完成编译和运行，平台可以较好保证不同提交之间的环境隔离和执行一致性。

这种执行方式虽然仍属于单机原型阶段的轻量容器化判题，但已经体现出统一镜像环境、按任务动态创建执行单元、资源限制和最小权限运行等关键思路。对于毕设原型而言，这样的实现复杂度和可展示性之间取得了较好的平衡。

除运行时约束外，容器生命周期管理同样属于安全隔离的一部分。系统在判题动作结束后无论成功还是失败都进入清理流程，尝试停止并删除对应容器，避免临时执行环境在宿主机上持续堆积。对在线编程评测平台而言，这种单次提交对应单次执行环境、执行后立即回收的策略虽然会带来一定容器启动开销，但能够换取更清晰的故障边界和更低的残留风险，尤其适合本科毕设原型阶段对稳定性与可说明性的要求。

\subsection{判题异常路径、错误回写与可观测性}

除编译失败、答案错误以及运行超时等学生侧常见结果外，工程实现还必须覆盖一类\textbf{系统侧异常}：例如 Docker 守护进程不可用、镜像缺失、题目或测试数据配置不完整、远程 Docker 连接失败等。此类问题若不在状态模型中单独区分，容易被误展示为普通 \texttt{CE}/\texttt{WA}，从而误导学生把环境问题当作算法问题反复修改。

本文将部分系统级失败映射为 \texttt{SE} 状态，并在 \texttt{Submission.message} 中写入可读的错误摘要，同时仍尽量保留已创建的提交记录，使前端能够展示一种失败但仍可追踪的状态。这与第四章状态流转设计相呼应，受理记录一旦生成，就应成为排错与复盘的锚点。与此同时，编译与运行阶段的输出在落库前进行长度截断，以避免极端日志撑爆数据库字段或拖慢页面渲染；在教学解释上，这一策略应被理解为保留足够定位信息，而不是无损保存完整 stderr。

从可观测性角度看，判题链路至少应能在日志中关联用户、题目、提交 id 与容器 id 这一最小追踪链。本文实现已将提交 id 贯穿在 \texttt{judge.ts}、Inngest 函数与编译运行模块中，便于定位事件投递、函数执行和容器运行各阶段的问题。原型阶段即使未接入分布式追踪系统，也应在关键异常分支打印结构化日志字段，便于在课程集中提交时快速判断瓶颈究竟出在异步函数吞吐不足，还是出在单机 Docker 资源耗尽\cite{kubernetesdocs}。

\section{AI 辅助子系统的流式响应与上下文构造实现}

AI 辅助子系统并非主判题链路的一部分，而是围绕客观判题已完成与正在编辑代码这两类时机，为学生提供解释性、提示性与对话性支持的附加能力。本节按总体架构、模型抽象、流式响应、结构化落库、编辑期同步辅助、上下文构造以及边界与兜底七个层次依次展开。其中，流式响应小节专门讨论实现工程中最关键的 SSE 风格数据流细节；这一细节直接决定了上下文聊天面板能否在网页上做到回复内容逐字浮现而非整段等待，并在概念上与第四章异步判题的状态推送同属长连接增量推送范畴。

\subsection{子系统总体架构与三类入口}

从工程实现看，平台中所有 AI 调用最终都汇聚到统一的模型抽象层，但在前端表现上对应三类相互独立的入口，分别是\textbf{提交后异步分析}、\textbf{编辑期同步辅助}与\textbf{上下文聊天}。提交后异步分析由 \path{src/app/actions/analyze-code.ts} 提供 \texttt{analyzeCode} Server Action，在判题主链路结束后被触发，结果作为 \texttt{CodeAnalysis} 行记录持久化。编辑期同步辅助由 \path{src/app/actions/analyze.ts} 中的 \texttt{analyzeComplexity}、\texttt{optimizeCode} 与 \path{src/app/actions/ai-improve.ts} 中的 \texttt{optimizeCode} 等 Server Action 提供，被工具栏按钮直接调用并以 JSON 形式同步返回。上下文聊天由 \path{src/app/api/chat/route.ts} 暴露的 Route Handler 与浏览器侧 \texttt{useChat} 钩子配合工作，是子系统中唯一以\textbf{流式响应}方式与用户交互的入口\cite{aisdk2024docs,aisdkreact2024docs}。

图~\ref{fig:ch5-ai-arch} 中三类入口在用户感知上差异明显：提交后分析对学生而言体现为几秒后页面上自动浮现一张评估卡片，编辑期辅助则体现为按钮加载圈停止后弹出 Diff 视图，而上下文聊天则需要让响应字符\textbf{在屏幕上实时浮现}。这种差异并非交互设计偏好，而是由后端 API 形态决定的：前两者使用 \texttt{generateText} 一次性返回，第三者必须使用 \texttt{streamText} 与底层模型建立长连接。下文先给出统一的模型层抽象，再分别讨论两类形态的实现要点。

\subsection{模型抽象层与 OpenAI 兼容 Provider 接入}

平台未硬编码任何具体厂商 SDK，而是通过 Vercel AI SDK 的 Provider 抽象统一访问远端模型\cite{aisdk2024docs}。具体而言，\path{src/lib/ai.ts} 通过 \texttt{createOpenAICompatible} 工厂方法，结合从环境变量读取的 \texttt{AI\_API\_KEY}、\texttt{AI\_BASE\_URL} 与 \texttt{AI\_MODEL} 三项配置，构造出一个可复用的 \texttt{model} 对象，供 AI 子系统其余模块统一调用。

这种组织方式有两层工程价值。\textbf{切换模型不改业务代码}：DeepSeek、月之暗面、智谱清言以及 OpenAI 自身都暴露 OpenAI 兼容 \texttt{/v1/chat/completions} 端点，将 \texttt{AI\_BASE\_URL} 与 \texttt{AI\_MODEL} 改成对应值即可在不重构上层逻辑的前提下切换\cite{deepseek2024api}；本文阶段实测使用 DeepSeek 服务。\textbf{敏感信息不进入版本库}：\texttt{API\_KEY} 通过 \texttt{getRequiredEnv} 从进程环境变量读取，缺失时直接抛错，避免开发期忘填、到生产期才崩溃这种延后失败\cite{owasp2021top10}。从架构视角看，模型层对应图~\ref{fig:ch5-ai-arch} 中部的统一模型层，所有调用方仅依赖 \texttt{generateText}/\texttt{streamText}/\texttt{tool} 这三个 SDK 顶层函数，与具体 Provider 解耦。

\subsection{基于 SSE 的聊天流式响应实现}\label{sec:ch5-ai-sse}

上下文聊天的难点并不在于能否拿到模型回复，而在于如何把回复\textbf{增量}送达浏览器并\textbf{增量}渲染，从而避免按下回车后等十几秒才一次性出现整段文字这种体验落差\cite{aisdk2024docs,aisdkreact2024docs}。本节按以下四步说明实现：为何需要流式、如何从模型一侧拿到流、如何把流回传给浏览器、以及浏览器侧如何消费这条流。

\noindent\textbf{第一，流式交互的必要性。}大语言模型的端到端推理延迟通常远大于普通 HTTP 请求：即使在不太长的上下文下，整段答案的产生时间常达数秒至十几秒。若服务端等模型生成完毕再一次性返回，则浏览器在此期间只能呈现一个加载中动画，用户感受到的首字节时延即等于完整生成时间。流式响应把首字节时延压缩到模型返回第一个 token 的时刻，并把后面的 token 持续推送到前端，使学生在阅读已到达的句子时模型仍在生成内容\cite{aisdk2024docs}。这种边生成边阅读的模式与传统 OJ 平台点完提交才出结果的同步交互截然不同，是当前对话型 AI 应用的事实标准\cite{rfc8895eventsource,whatwgeventsource}。

\noindent\textbf{第二，服务端流式返回。}\path{src/app/api/chat/route.ts} 是整个聊天能力的入口，其本体非常精简：在 \texttt{POST} 处理函数内解析请求体中的对话历史 \texttt{messages}，以预设角色与行为约束作为 \texttt{system} 提示词，调用 SDK 的 \texttt{streamText} 取得流式响应对象，再经 \texttt{toDataStreamResponse} 封装为 Web \texttt{Response} 直接返回。与此同时通过 \texttt{maxDuration = 30} 向 Next.js 声明该 Route Handler 的时长上限，用于配合无服务器部署平台对长连接的处理\cite{nextjsdocs}。

这一精简实现涉及三个关键 API：\texttt{streamText} 通过 OpenAI 兼容 Provider 向远端模型发起 \texttt{stream:true} 的 Chat Completions 请求，返回一个包装后的流对象；\texttt{toDataStreamResponse} 把该流封装为符合 Vercel AI SDK Data Stream Protocol 的 Web \texttt{Response}\cite{aisdk2024docs}；\texttt{maxDuration} 则把单条长连接最长允许保持多久这一部署级约束以代码声明方式与业务文件绑定，便于迁移时同步迁出\cite{nextjsdocs}。

需要严谨说明的是，本文所称的 SSE 风格流式响应在协议层与传统 \texttt{text/event-stream} 标准 SSE 并不完全等同：标准 SSE 由 WHATWG 在 HTML 规范中定义，要求响应 \texttt{Content-Type: text/event-stream}、按 \texttt{event:}/\texttt{data:} 行格式封装，并由浏览器原生 \texttt{EventSource} 接口解析\cite{whatwgeventsource,rfc8895eventsource}。Vercel AI SDK 的 Data Stream Protocol 借鉴了相同的一行一事件、按行解析的思想，但出于可携带二进制安全字符串、支持 POST 请求体以及兼容流式 fetch 的考虑，使用 \texttt{Content-Type: text/plain; charset=utf-8} 与自定义前缀字符，例如 \texttt{0:}、\texttt{2:}、\texttt{e:}、\texttt{f:}，区分文本块、工具调用、错误与完成等帧类型，并依靠 HTTP/1.1 chunked transfer encoding 实现分块推送\cite{aisdk2024docs,rfc7230chunked}。两者的共同特征都是在单条长连接上把一次响应拆为多次增量帧，因此在工程语境下统称为 SSE 风格的增量流式响应是合适的；但读者应注意它并非通过浏览器 \texttt{EventSource} 接口消费，而是由 SDK 在 fetch 之上自行解析。

\noindent\textbf{第三，客户端增量渲染。}浏览器侧的 \path{src/features/problems/bot/components/form.tsx} 没有直接处理 SSE 帧，而是依赖 \texttt{@ai-sdk/react} 的 \texttt{useChat} 钩子\cite{aisdkreact2024docs}。组件挂载时把当前题目描述以 \texttt{role: "system"} 形式作为 \texttt{initialMessages} 注入，钩子返回 \texttt{messages}、\texttt{input}、\texttt{setMessages}、\texttt{handleSubmit} 等受控值与回调，由组件直接消费用于渲染对话区与输入框。

该钩子在内部完成了三件事：调用 \texttt{fetch("/api/chat", \{ method: "POST", body: JSON.stringify(\{ messages \}) \})} 并保留返回的 \texttt{ReadableStream}；逐 chunk 读取流并按 Data Stream Protocol 行协议解析出文本片段、工具调用片段或结束帧；把解析得到的当前助手消息对象不断 \texttt{setMessages} 到 React 状态，使 \texttt{messages} 数组在每个 chunk 到达时都触发一次最小化重渲染。\path{form.tsx} 仅消费 \texttt{messages}，并通过 \texttt{MdxPreview} 把已到达的 Markdown 文本即时渲染为代码块、列表、强调等富文本，使用户看到一种逐段浮现的回复效果。

图~\ref{fig:ch5-ai-sse-seq} 给出了从用户按下发送到屏幕上看到首个字符为止的完整时序。可以看到，关键路径上没有任何一段以整段等待为前提：模型按 token 增量产出，Provider 解析 \texttt{[DONE]} 之前的每条 SSE chunk，SDK 将其重新包装为 Data Stream 帧，Route Handler 借 chunked transfer 透传给浏览器，浏览器侧 \texttt{useChat} 再驱动 React 增量重渲染。

\noindent\textbf{第四，编辑期辅助采用非流式返回。}需要补充澄清的是，并非所有 AI 调用都适合做成流式。编辑期的复杂度分析与代码优化按钮被设计为一次性返回 JSON。按钮产出要么是两个枚举字段，要么是一份完整代码，没有逐字阅读需求。前端也需要拿到整段输出后再做 \texttt{JSON.parse} 与 \texttt{zod} 校验，否则中途状态既无意义也容易引起渲染抖动。因此这两类入口在 \path{analyze.ts} 中使用 \texttt{generateText} 而非 \texttt{streamText}，体现了按交互形态选择 API 的工程原则。

\subsection{提交后异步分析与 Tool Calling 强约束}

提交后异步分析在 \path{src/app/actions/analyze-code.ts} 中实现，是 AI 子系统中字段最多、约束最强的入口，也是论文里 \texttt{CodeAnalysis} 表的唯一写入方。其难点不在调用模型本身，而在于\textbf{如何让概率性输出始终能稳定落到关系型表的特定列上}。

\begin{figure}[htbp]
  \centering
  \resizebox{0.92\textwidth}{!}{\input{figures/ai_analyze_pipeline.tex}}
  \caption{提交后异步分析的状态流转与 Tool Calling 调用关系示意}
  \label{fig:ch5-ai-analyze-pipeline}

\noindent\textbf{第一，异步状态机与判题主链路解耦。}\texttt{analyzeCode} 进入函数体后立即创建一条 \texttt{status="QUEUED"} 的 \texttt{CodeAnalysis} 记录，再在 \texttt{try} 块内推进到 \texttt{PROCESSING}，调用模型，并在工具回调内完成 \texttt{COMPLETED} 写入；任何一步异常都会被 \texttt{catch} 捕获并把状态置为 \texttt{FAILED}，见图~\ref{fig:ch5-ai-analyze-pipeline}。这种先建占位记录再推进状态的模式有两个直接好处。前端无需轮询时使用复杂的记录是否存在判断逻辑，统一查同一行的 \texttt{status} 字段即可。即便模型返回超时或调用方进程被回收，最终落库状态仍能反映任务启动但未完成这一事实，便于教师与运维人员排查。在与判题主链路的关系上，分析任务由 Server Action 异步触发但不阻塞判题返回，因此即便 AI 服务故障，学生仍可拿到 \texttt{AC}/\texttt{WA} 等标准结果，仅看不到分析卡片。

\noindent\textbf{第二，Tool Calling 强约束输出。}为避免让模型用 JSON 自由文本回答再由正则解析这一脆弱方案，本实现采用 Vercel AI SDK 的 \texttt{tool} 与 \texttt{toolChoice} 联合机制\cite{aisdk2024docs}。在 \texttt{generateText} 调用中声明唯一一个名为 \texttt{saveCodeAnalysis} 的工具，其入参由 \texttt{zod} 直接描述为一组结构化字段，包含时间复杂度、空间复杂度、五项 0 到 100 整数分数与一段长文本反馈，详见表~\ref{tab:ch5-codeanalysis-fields}。其回调函数直接以这些字段更新对应 \texttt{CodeAnalysis} 记录并把状态推进到 \texttt{COMPLETED}。同时通过 \texttt{toolChoice} 指定该工具为强制调用项，使模型在本次响应中必须以工具调用形式返回结构化结果，不允许产生自由文本。

这一调用形态背后包含三个工程要点：\textbf{参数即 Schema}、\textbf{回调即落库} 与 \textbf{强制工具选择}。工具入参直接以 \texttt{zod} 描述，AI SDK 在请求时会把它编译为 OpenAI 兼容的 JSON Schema 注入到 \texttt{tools} 字段；模型在响应中如果声明调用该工具，必须按 Schema 提供参数，否则响应会被拒收\cite{aisdk2024docs}。工具的 \texttt{execute} 回调并不是把返回值交还给模型，而是拿到参数后立刻写库，这就把 SDK 的 Tool Calling 链路当作一种服务端侧结构化回调来使用，而非按多轮 Agent 的方式驱动，从而避免引入不必要的多轮调用复杂度。通过 \texttt{toolChoice} 指定命令模型\textbf{必须}调用该工具而不能直接产生自由文本，可把模型偶发格式错误收敛为字段缺失这一较轻形态。结合工具入参中所有字段均声明为 \texttt{optional} 的设计，最坏情况下也只会出现分析记录字段不全，而不会出现整条记录无法落库的情况，这与传统通过正则匹配 JSON 字符串的脆弱方案形成鲜明对比。

\subsection{编辑期同步辅助：复杂度分析与代码优化}

编辑器工具栏暴露的复杂度分析按钮与代码优化按钮分别由 \path{src/app/actions/analyze.ts} 中的 \texttt{analyzeComplexity} 与 \texttt{optimizeCode} 实现，二者均使用非流式 \texttt{generateText}，随后再做严格的 JSON 解析。

复杂度分析的提示词将 \texttt{Complexity} 取值集合显式写入 \texttt{system} 上下文，八个枚举包括 \texttt{O(1)}、\texttt{O(logN)}、\texttt{O(N)} 等，并要求模型仅返回形如 \texttt{\{"time":"O(N)","space":"O(1)"\}} 的 JSON 对象；返回后立刻用 \texttt{AnalyzeComplexityResponseSchema.safeParse} 校验。这种枚举集合写在提示词中、JSON Schema 写在解析端的双向收敛策略，使最终落到前端的字段一定属于预定义集合，避免出现 \texttt{O(N)\^2}、\texttt{Linear} 等不规范字符串导致雷达图与状态徽章渲染失败。

代码优化按钮则在 \texttt{ai-improve.ts} 中拼装一段更长的提示词：除当前代码与可选错误信息外，还从数据库查询当前题目的英文描述，若缺失则回退到中文，并读取该题目下所有语言的模板代码，再在末尾要求模型仅返回 \texttt{\{ optimizedCode, explanation, issuesFixed \}} 形式的 JSON。值得注意的是，模型实际输出常常包含 \texttt{```json ... ```} 围栏，因此实现先用正则 \texttt{/```(?:json)?\textbackslash s*([\textbackslash s\textbackslash S]*?)```/} 提取代码块内 JSON，再回退到匹配整段文本中第一段花括号包裹内容的宽松策略，最后用 \texttt{OptimizeCodeOutputSchema.safeParse} 做 zod 校验。这种先做宽容解析、再做严格校验的两段式处理避免了把模型偶发的 Markdown 包装直接当作错误抛回前端。

返回到前端后，优化结果不会静默覆盖原代码，而是被存入 \texttt{useProblemEditorStore} 的 \texttt{optimizedCode} 字段；只有当 \texttt{optimizedCode} 非空时，工具栏才会出现 \texttt{ViewToggleButton}，允许学生在 Monaco 普通编辑器与 Diff 编辑器之间切换查看改动。这种原代码不可破坏、改动显式可见、最终由学生决定是否采纳的处理方式与第三章中关于 AI 可控性的非功能要求一致。

\subsection{聊天面板的上下文构造与题面注入}

聊天面板 \path{form.tsx} 的初始消息中放入了一条 \texttt{role: "system"} 的题面消息，格式为 \texttt{Problem description: ...}；并在每次表单提交时再额外把当前编辑器代码以 Markdown 围栏 \texttt{\textasciigrave\textasciigrave\textasciigrave}\textit{language}\textellipsis\texttt{\textasciigrave\textasciigrave\textasciigrave} 包装为另一条 \texttt{role: "system"} 消息，通过 \texttt{setMessages} 追加到对话上下文末尾，再调用 \texttt{handleSubmit} 触发本轮请求。

这种题面常驻、代码现注入的策略在工程上具有两点考虑：第一，题面在用户进入页面时即固定，将其作为初始系统消息可以避免重复传输；第二，代码会被频繁修改，每次提问时拼一份当前代码进入 \texttt{messages}，可保证模型看到的始终是用户\textbf{此刻屏幕上的代码}而非任何缓存版本，这对于回答诸如这一行为什么运行不出来这类具体问题至关重要。

把题面与代码作为 \texttt{system} 消息而非 \texttt{user} 消息也有讲究。OpenAI 兼容协议中 \texttt{system} 消息的语义是模型应当将其作为既定背景理解，与用户实际在提的问题相分离\cite{deepseek2024api}；这样回答时模型不容易把题面和代码反复抄回给学生，而是聚焦于回答本轮提问。结合提示词中要求模型以用户当前所用语言回复这一约束，最终用户得到的就是这样一种体验：模型既知道题目、又知道我现在写的代码，并用我熟悉的语言简洁地回答。

\subsection{故障兜底与教学边界}

AI 子系统的失败兜底策略可归纳为三层。第一层是\textbf{对判题主链路无影响}：所有 AI 调用都以 Server Action 或独立 Route Handler 形式存在，不在 \texttt{judge.ts} 主链路上同步等待，因而即使模型不可达、配额耗尽或返回格式错误，学生仍能完成提交并获得标准 \texttt{AC}/\texttt{WA}/\texttt{TLE} 等结果。第二层是\textbf{结构化字段降级}：在 \texttt{analyze-code.ts} 中所有 zod 字段均为 \texttt{optional}，意味着若模型返回缺少某些维度，最终落库的也只是部分字段为空，而不是整条记录写入失败，前端只需对空值显示占位即可，不影响其他字段渲染。第三层是\textbf{状态可观测}：所有失败分支都把状态写为 \texttt{FAILED} 并保留时间戳，配合后台日志可以快速判断是模型调用前异常、模型本身超时，还是工具回调内 SQL 写入失败。

教学边界方面，本子系统遵守第三章给出的 AI 可控性原则：聊天面板的 system prompt 强调要用用户语言回复并保持简洁，而非直接给出完整答案；优化代码不会覆盖原代码，且需用户主动按按钮才会触发；分析结果与客观判题状态分离存储，从数据模型层面阻断了 AI 评分污染判题结果的可能。这些工程化处理使 AI 在系统中始终扮演解释与提示的角色，而非充当裁判。

\subsection{国际化、多语言与主题一致性}

平台的多语言能力由数据层与界面层共同构成。数据层借助 \texttt{ProblemLocalization} 按 \texttt{locale} 组织题目标题、题面描述与题解说明，使同一道题目在不同语言下呈现一致的题面结构；界面层则需要系统化的国际化 i18n 组织来承载导航、按钮、错误提示、判题状态解释、AI 面板标题等高频文本，否则会出现题面是英文但按钮仍是中文这一类割裂体验。

界面 i18n 工程实现采用 \texttt{next-intl} 与 Next.js App Router 结合：服务端组件通过 \texttt{getTranslations}/\texttt{getLocale} 读取当前语言环境下的文案，客户端组件通过 \texttt{useTranslations}/\texttt{useLocale} 绑定交互控件标签；语言偏好通过 Cookie 在请求之间保持，使刷新与导航后仍能获得一致的语言上下文\cite{nextjsdocs}。翻译资源以消息字典形式按命名空间集中维护，页面与组件只引用键路径而不硬编码长字符串。新增页面时可借助键缺失检测尽早发现漏翻译；若课程方需要调整术语例如将提交统一改为评测提交，只需改字典而无需在大量组件中全文搜索替换；服务端渲染路径与客户端 hydration 路径读取同一套消息源，可以减少首屏与二次渲染之间的语言不一致问题。

除语言外，工作区还实现了深浅色主题切换，并使普通页面、Monaco 编辑器与差异对比编辑器使用对应主题，避免题面区域、代码区域与 Diff 视图在切换主题后出现明显割裂；这种语言与主题协同收敛的处理方式满足了长时间阅读、对比代码的基本需求。第六章交互测试中的多语言切换项 I-02 即用于核验界面文本与题面语境的一致性，而不仅是验证语言切换功能本身。

\subsection{Monaco 编辑器与基于 LSP 的 IDE 级语言服务}

本节结合实现代码说明编辑器能力与语言服务链路，并聚焦与编码体验直接相关的关键模块。

许多传统在线评测系统仍采用轻量文本框或简化编辑器，常见能力止步于关键字着色与基础缩进。对入门学生而言，这类编辑器在拼写错误、漏写分号、括号不匹配、类型不匹配等高频问题上缺乏即时反馈，学生往往只能依赖编译器输出的大量信息自行定位；在题目规模变大或模板宏较多时，这种反馈链路会显著拉长试错周期。工程实现策略是将浏览器端编辑体验尽量对齐本地 IDE：以微软 Monaco Editor 作为代码编辑内核\cite{monacoeditorrepo}，并通过 Language Server Protocol 即 LSP 与独立的 C/C++ 语言服务器通信，使补全、诊断、悬停提示、签名帮助等能力以标准化方式进入 Web 工作区\cite{lsp2024spec,monacolanguageclientrepo}。

\noindent\textbf{第一，前端依赖与编辑器基础能力。}题目求解页的实现栈以 \texttt{@monaco-editor/react} 与 \texttt{monaco-editor} 为核心，并配合 \texttt{monaco-languageclient}、\texttt{vscode-languageclient} 与 \texttt{vscode-ws-jsonrpc} 将 LSP 的 JSON-RPC 消息映射到浏览器 \texttt{WebSocket} 传输层\cite{monacolanguageclientrepo}。编辑器默认选项在 \path{src/config/editor.ts} 中集中配置，启用 ligatures、括号配对着色、缩进参考线、粘性滚动、平滑滚动与自动换行等特性，使长时间读码与改码的视觉负担更低。主题方面，工程使用 Shiki 高亮器并通过 \texttt{@shikijs/monaco} 将配色注册到 Monaco，从而使代码区与站点深浅色主题保持一致，与图~\ref{fig:dark-theme-workspace} 所示工作区观感一致。

\noindent\textbf{第二，语言服务端点注入与连接建立。}语言服务的连接参数并不写死在前端常量中，而是由服务端在渲染题目页时从数据库读取并注入。具体而言，\path{src/features/problems/code/components/content.tsx} 在服务端执行 \texttt{prisma.languageServerConfig.findMany()}，将返回的 \texttt{LanguageServerConfig} 列表传入 \texttt{ProblemEditor}，再下发到 \texttt{CoreEditor}\cite{prismadocs}。数据模型在 \texttt{schema.prisma} 中以语言为主键记录 \texttt{protocol}、\texttt{hostname}、\texttt{port} 与 \texttt{path} 等字段，使同一套前端代码可以在本地 Compose、内网部署或公网域名等不同环境下复用，只需调整种子数据或数据库配置即可。

在浏览器侧，\path{src/components/core-editor.tsx} 根据当前语言选择匹配的 \texttt{LanguageServerConfig}，拼接出 \texttt{WebSocket} URL 并建立连接；连接建立后创建 \texttt{MonacoLanguageClient} 并启动，使 Monaco 与语言服务器进入同一套 LSP 会话。编辑器挂载完成后才发起连接，卸载时停止 client，避免页面切换造成资源泄漏。工具栏中的 \texttt{LSP} 状态指示组件 \path{lsp-connection-indicator.tsx} 通过观察 \texttt{WebSocket} 的就绪状态给出可视化反馈，让学生明确当前是否具备语言级诊断能力，这与仅依赖提交后判题反馈的体验有本质差异。

\noindent\textbf{第三，容器化语言服务与 Compose 编排。}语言服务器本身同样以容器方式运行，便于与主服务生命周期对齐。工程 \texttt{compose} 配置中除 \texttt{judge4c} 与 \texttt{postgres} 外，还包含 \texttt{lsp-c} 与 \texttt{lsp-cpp} 两个服务镜像。二者基于 \path{docker/lsp/clangd} 构建，在容器内通过 \texttt{jsonrpc-ws-proxy} 将 \texttt{WebSocket} JSON-RPC 转发到 \texttt{clangd} 进程，\texttt{servers.yml} 中声明 \texttt{/usr/bin/clangd} 及后台索引参数。主服务通过 \texttt{depends\_on} 等待语言服务健康检查通过后再启动，从而降低页面已打开但语言服务尚未就绪的偶发体验问题。该编排方式也与前文所述判题执行与辅助能力尽量容器化、可替换的总体思路一致\cite{dockerdocs,kubernetesdocs}。

\noindent\textbf{第四，与传统 OJ 编辑器的对比价值。}结合上述实现，平台在编码阶段能够提供三点价值：\textbf{错误前移}，在提交前即可通过诊断标记暴露大量语法与类型问题，减少无意义提交；\textbf{反馈可解释}，诊断与补全携带位置与符号信息，比单纯依赖编译器 stderr 更接近课堂讲解表达习惯；\textbf{工程可运维}，语言服务与业务站点解耦，可按语言横向扩容或替换版本，而不必随每次业务发版耦合发布。对本科教学场景而言，这类能力并不替代判题主链路客观性，但能显著降低学生在模板代码附近卡住的概率，从而把更多认知资源留给算法与测试设计本身。

\noindent\textbf{第五，工具栏对编辑器与 AI 能力的统一收口。}上述 LSP 能力与第~\ref{sec:ch5-ai-sse}~节所述 AI 辅助能力最终都会汇聚到题目工作区上方的代码工具栏 \path{src/features/problems/code/components/toolbar/code-toolbar.tsx}。工具栏把语言切换、模板加载、\texttt{LSP} 状态指示灯、AI 相关按钮 \texttt{AnalyzeButton}、\texttt{OptimizeButton}、\texttt{ViewToggleButton} 与撤销、重做、格式化等基础编辑动作整合到同一行内，使学生在编码过程中无需离开视线焦点即可触发诊断、复杂度分析、优化建议与 Diff 对比等动作。表~\ref{tab:ch5-editor-toolbar} 汇总了工具栏中各能力的实现方式与教学作用，可与图~\ref{fig:problem-workspace} 所示界面对照查看。

\subsection{响应式布局与多终端适配}

除桌面端常规使用场景外，当前前端实现还显式考虑了平板与移动端访问时的界面退化策略。系统通过独立的移动端检测逻辑识别当前视口宽度，并在侧边栏等高频交互区域中区分桌面端与移动端布局方式：在桌面端，工作区可维持多面板并列或可折叠侧栏的组织形式；在移动端，则优先采用抽屉式面板承载侧边内容，以避免在狭窄屏幕中出现过度拥挤的固定布局。这意味着平台虽然主要服务于桌面编程训练，但并未把小屏设备完全排除在可用范围之外。

\subsection{运行环境与本地部署}

\section{实现边界说明}

本节用于说明第五章实现结果与第四章设计目标之间的对应关系，明确已完成主链路与系统边界，避免将设计项与已实现功能混写。

判题入口 \texttt{judge} 位于 \path{src/app/actions/judge.ts}，在接收请求后先完成参数校验并创建状态为 \texttt{QD} 的提交记录，随后通过 \texttt{inngest.send} 投递事件；\path{src/inngest/functions/process-submission.ts} 订阅该事件并异步执行容器准备、编译与逐用例运行流程，底层执行由 \path{src/lib/judge-runtime.ts} 提供。该实现将请求受理与耗时执行解耦，前端可先获得已受理状态，再随着后台处理持续看到状态推进。

与主判题不同，\texttt{CodeAnalysis} 使用独立状态枚举，例如 \texttt{QUEUED}、\texttt{PROCESSING}，由 \texttt{analyzeCode} 在客观判题完成后异步触发，体现主结果确定、解释层后置的拆分方式。判题状态推送与语言服务同样基于 WebSocket 长连接，但二者在频道与事件语义上保持分离：前者通过 \texttt{problem-\{id\}} 与 \texttt{submission-\{id\}} 频道推送提交状态刷新，后者用于编辑期 LSP 会话。

在课程化能力方面，本文已完成课程、选课关系、作业及作业题目关联等核心数据结构，并将作业上下文与提交记录建立关联。基于这一结构，教师端可进行课程维护、学生管理、作业创建与发布及统计查看，学生端也可在课程语境下进入作业并完成提交。总体而言，现有题库、提交、判题轨迹与 AI 分析已经形成可运行的数据闭环。

\section{本章小结}

本章围绕平台核心模块的实现结果，说明了数据模型、题库组织、在线提交、容器化判题、AI 辅助分析、前端工作区、身份认证与 LSP 等关键内容。结果表明，系统已可在单机环境完成从登录、做题、提交到结果反馈的完整流程，课程与作业组织能力也已形成基本闭环；异步判题与实时状态推送也已接入主链路。
