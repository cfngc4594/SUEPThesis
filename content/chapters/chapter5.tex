\chapter{平台核心功能实现}

\section{本章说明}

结合当前项目实现情况，平台采用全栈 Web 应用方式组织前后端能力：前端负责题目展示、代码编辑、提交记录查看与 AI 反馈交互，后端负责题目读取、提交入库、判题调度、容器调用和分析结果持久化。虽然项目部署为统一工程，但在代码职责上已经形成了相对清晰的模块划分。

本章重点说明与论文主题最直接相关的核心实现，即题目读取、代码提交、容器化判题、AI 辅助分析以及前端工作区。对于教师管理、学生管理和复杂统计面板等配套页面，虽然工程中也有一定实现，但本文不将其作为主成果展开。

当前系统用户模型以 User 实体为核心，记录用户名称、邮箱、密码、头像和角色等信息。角色字段用于区分管理员、教师与普通学生等不同访问主体，并结合认证模块完成登录后的身份识别。对于平台主链路而言，角色机制主要影响题目维护权限和后台访问范围，而不改变学生提交判题的核心流程。

\subsection{题目内容与模板数据设计}

题目实体 Problem 负责描述 displayId、难度、是否发布、时间限制、内存限制等基础属性。其中 displayId 用于面向用户的题号展示，timeLimit 与 memoryLimit 则直接影响判题执行阶段的资源约束。ProblemLocalization 通过 problemId、locale 和 type 组合唯一确定一条本地化内容，用于分别存储题目标题、题面描述和题解内容；Template 则通过 problemId 与 language 的组合存储不同语言的模板代码。

从数据一致性角度看，当前模式设计并不是把所有文本和代码都堆在同一张表中，而是通过复合主键和唯一约束保证多语言内容与模板代码的组织稳定性。例如，同一道题目在同一种语言下只能存在一份模板代码，同一道题目在同一种语言和同一种内容类型下也只能存在一份本地化文本。这种设计既减少了重复数据，也让前端读取题目详情时更容易获得确定结果。

Submission 是整个平台中最关键的业务实体之一，用于存储语言类型、源代码、判题状态、错误信息、时间使用量和内存使用量等信息。Testcase 与 TestcaseInput 共同描述标准测试数据；TestcaseResult 则用于保存每个用例执行后的结果。这样的结构使判题过程能够精细记录到“提交级”和“用例级”两个层面，便于展示提交详情，也便于后续统计和教学分析。

CodeAnalysis 用于保存 AI 辅助分析结果，它通过 submissionId 与 Submission 建立一对一关系，并使用独立状态字段跟踪分析任务的处理阶段。这样一来，AI 分析既可以异步运行而不阻塞主判题流程，也可以与客观判题结果保持分离存储。

\section{题库与题目组织}

题库管理模块主要由 Problem、ProblemLocalization、Template 和 Testcase 等实体支撑。其中 Problem 负责题目基础约束，ProblemLocalization 负责题目文字内容，Template 负责不同语言的模板代码，Testcase 及其输入项负责标准评测数据。这样的设计使题目内容维护、前端展示和后端判题能够围绕同一份题目数据协同工作。

从功能边界上看，题库管理模块的主要任务是为判题主链路提供准确、完整和可维护的数据来源，而不是在论文中展开复杂后台交互细节。因此，本文只描述与题目内容组织、模板代码和测试数据直接相关的实现。

系统同时支持按语言维度为题目保存模板代码，使学生进入题目页后可以直接获得对应语言的初始代码。测试数据则通过 Testcase 与 TestcaseInput 共同组织，其中 TestcaseInput 保存有序输入项，便于在运行阶段按顺序组合为标准输入流。

在题目内容组织方式上，系统将标题、题面描述和题解说明分别以 ProblemLocalization 的不同 type 存储，并配合 locale 字段支持中英文等多语言内容读取。当前实现中，题目读取动作会统一查询题目基本信息、模板代码、测试用例及其输入项、本地化内容等数据，并将题面描述序列化为可直接渲染的内容对象返回前端。

题目读取模块并不是把数据库内容直接透传给前端，而是先在服务端完成一次聚合和整理。系统会在单次查询中同时带出模板代码、测试用例及其输入项，以及符合当前语言环境的本地化文本；随后再提取标题、题面描述和题解字段，并将题面描述序列化为 MDX 数据结构。这样处理后，前端拿到的数据已经更接近可直接渲染的形态，页面层不需要过多了解底层表结构。

当前实现对本地化内容采用了比较直接的读取策略，即按当前 locale 查询匹配内容，不在读取层额外引入复杂回退规则。这样处理的好处在于实现简单、行为清楚，适合当前原型阶段；如果后续需要面向更正式的多语言教学场景，还可以在服务端补充“当前语言缺失时回退到默认语言”的策略。

\subsection{提交受理与状态流转}

在提交入口处，系统首先校验用户是否登录、题目是否存在、测试用例是否存在以及对应语言的 Docker 配置是否完整。通过这些前置检查，可以避免无效请求直接进入判题流程。校验通过后，系统创建 Submission 记录，并以 Pending 状态作为判题起点。随后，源代码被封装为指定文件名写入 tar 数据流，再上传到新建的容器工作目录中，为后续编译执行做准备。

将 Submission 记录放在编译和运行之前创建，具有比较明确的工程意义。这样做后，系统从用户点击提交开始就有了稳定的状态载体，前端可以立即展示记录，后续即使编译、运行或容器调用失败，也能把错误统一回写到同一条记录中。同时，这种处理方式也更容易与后续异步任务队列模型衔接。

\subsection{编译流程实现}

编译阶段会先把 Submission 状态更新为编译中，再根据语言类型生成对应命令。当前实现中，C 语言通过 gcc -O2 编译为 main，C++ 通过 g++ -O2 编译为 main。为避免编译日志无限增长，系统对编译输出设置了长度限制；若编译失败，则将错误信息写回 Submission.message，并把状态更新为 Compilation Error。

编译输出长度限制是一个容易被忽略但实际很有必要的细节。若对编译器标准错误流完全不做限制，极端情况下可能产生非常长的错误日志，不仅增加数据库写入压力，也会影响页面展示和网络传输效率。当前实现通过受限写入流截断编译输出，只保留限定长度内的错误信息。对于教学场景而言，这样的处理通常不会影响学生定位常见语法错误。

\subsection{运行与用例判定实现}

在运行阶段，系统按测试用例顺序逐个创建执行实例，将排序后的输入参数写入标准输入流，再根据程序输出与标准输出进行比较，从而判定答案是否正确。若题目配置启用了裁剪空白字符比较，则输出对比采用 trim 方式；否则按原始输出严格匹配。每个用例的输出、时间消耗和正确性结果都会保存到 TestcaseResult。

若某个测试用例触发答案错误、运行错误、时间超限或内存超限，系统会立即写入对应的 TestcaseResult 记录，并终止后续用例执行。只有当前一个用例返回正常执行状态时，才会继续处理下一个用例。这一实现符合在线评测系统常见的短路判题思路，也有助于节省执行资源。

当所有测试用例均通过后，系统会统计该提交下各用例的时间消耗，并结合容器运行统计更新最终的时间使用量和内存使用量，再把 Submission 的状态设置为 Accepted。这样，提交记录不仅保存了最终结果，还能保留一定的性能信息，为后续结果展示和教学分析提供依据。

在具体执行方式上，系统并不是把所有输入一次性拼接后批量运行，而是按测试用例顺序逐个执行。每个测试用例对应的输入项会先按 \texttt{index} 字段排序，再拼接为标准输入流写入容器进程。这样可以更准确地记录每个用例的输出和耗时，也便于在出现 \texttt{WA}、\texttt{RE} 或 \texttt{TLE} 时快速定位首个失败用例。

当所有测试用例都通过后，系统会从各个 TestcaseResult 中提取非空时间并取最大值作为本次提交的时间摘要，而不是简单取最后一个用例的耗时。这样更接近在线编程评测平台常见的统计方式。内存使用量则通过容器统计信息提取峰值，为后续页面展示和性能分析提供摘要依据。

\subsection{资源约束与安全隔离实现}

容器创建逻辑中，系统为每次判题准备独立运行环境，设置工作目录、内存限制，并默认禁用网络，从而降低恶意代码或异常程序对宿主系统的影响。由于每次提交都在新的容器环境中完成编译和运行，平台可以较好保证不同提交之间的环境隔离和执行一致性。

这种执行方式虽然仍属于单机原型阶段的轻量容器化判题，但已经体现出统一镜像环境、按任务动态创建执行单元、资源限制和最小权限运行等关键思路。对于毕设原型而言，这样的实现复杂度和可展示性之间取得了较好的平衡。

除运行时约束外，容器生命周期管理同样属于安全隔离的一部分。当前实现会在判题动作结束后无论成功还是失败都进入清理流程，尝试停止并删除对应容器，避免临时执行环境在宿主机上持续堆积。对在线编程评测平台而言，这种“单次提交对应单次执行环境、执行后立即回收”的策略虽然会带来一定容器启动开销，但能够换取更清晰的故障边界和更低的残留风险，尤其适合本科毕设原型阶段对稳定性与可说明性的要求。

\section{AI 辅助分析与解释性反馈}

AI 辅助反馈模块的作用并非替代评测，而是利用模型的代码理解和文本生成能力，为学生提供复杂度分析、质量评价和改进建议。该模块对应工程中的分析动作与详情展示逻辑，属于“后置辅助”能力，而不是主判题链路的一部分。

\subsection{响应式布局与多终端适配}

除桌面端常规使用场景外，当前前端实现还显式考虑了平板与移动端访问时的界面退化策略。系统通过独立的移动端检测逻辑识别当前视口宽度，并在侧边栏等高频交互区域中区分桌面端与移动端布局方式：在桌面端，工作区可维持多面板并列或可折叠侧栏的组织形式；在移动端，则优先采用抽屉式面板承载侧边内容，以避免在狭窄屏幕中出现过度拥挤的固定布局。这意味着平台虽然主要服务于桌面编程训练，但并未把小屏设备完全排除在可用范围之外。

从具体使用方式上看，题目阅读、提交记录回顾、AI 问答和结果查看等信息密集型区域，在桌面端更适合并列呈现，以支持“边看题、边写码、边复盘”的并行操作；而在平板或手机端，更合理的策略是让核心编辑区域保持主要可见，同时将次级面板收纳为按需展开的区域。当前实现采用这种“核心内容常驻、辅助内容按需展开”的方式，使同一工作区能够适配多类终端。

\subsection{多语言支持与主题一致性}

当前系统的多语言支持由数据层和界面层共同实现。数据层通过 \texttt{ProblemLocalization} 按 \texttt{locale} 组织题目标题、题面描述和题解说明；界面层提供语言切换组件，并通过 Cookie 记录用户偏好。测试结果表明，中文与英文界面可以正常切换，题面内容和主要界面文本能够保持一致。这一设计首先满足了双语题面展示需求，也为后续扩展更多语种保留了基础结构。

除语言外，当前前端还实现了深浅色主题切换，并使普通页面、Monaco 编辑器和差异对比编辑器使用对应主题。这样可以避免题面区域、代码区域和 Diff 视图在切换主题后出现明显割裂，满足长时间阅读和对比代码的基本需求。

\subsection{上下文感知的 AI 问答面板}

除前述“提交后分析”和“编辑中分析”外，当前平台还在题目工作区中提供了独立的 AI 问答面板。该面板会读取当前题目的本地化题面，并在用户提问时把当前编辑器代码一并作为上下文发送给模型，因此回答通常能够直接围绕当前题目和当前代码展开。

\subsection{运行环境与本地部署}

在运行环境支持上，系统通过配置项区分本地 Docker 模式和远程 Docker 模式。若在本地模式下运行，平台直接通过宿主机 Docker 套接字管理容器；若在远程模式下运行，则根据协议、地址、端口和证书建立远程 Docker 连接。这样的设计使判题执行环境能够与 Web 服务解耦，也为后续迁移判题节点提供了基础。

本轮已在本地环境中完成基础部署验证。通过 \texttt{docker compose -f compose.local.yml up -d postgres} 启动数据库容器后，终端结果显示 \texttt{postgres} 服务已进入 \texttt{healthy} 状态；随后执行 \texttt{bun install} 完成依赖安装并触发 Prisma Client 生成，执行 \texttt{bunx prisma migrate deploy} 成功应用现有 10 个数据库迁移，执行 \texttt{bunx prisma db seed} 完成种子数据初始化。在此基础上，项目还通过了 \texttt{bun run build} 生产构建校验，构建输出中可见 \path{/problemset}、\path{/problems/[problemId]}、\path{/dashboard} 以及后台管理相关核心路由均已成功参与构建。由此可以说明，系统在当前阶段已经具备从数据库准备、模式迁移、数据初始化到前端生产构建的完整本地运行基础。图~\ref{fig:local-dev-env}给出了系统本地运行界面与开发终端状态，可作为本地演示环境正常工作的直接证明。

从当前仓库提供的容器编排文件来看，系统部署并不是单容器模式，而是由 Web 主服务、两个语言服务容器和数据库容器共同组成。主服务 \texttt{judge4c} 负责页面访问、业务处理和判题入口；\texttt{lsp-c} 与 \texttt{lsp-cpp} 分别为 C 和 C++ 编辑器提供语言服务支持；\texttt{postgres} 则负责业务数据持久化。这说明项目虽然以本科毕设原型为目标，但在运行支撑层面已经具备一定的工程完整性。

此外，部署配置中已经显式考虑了健康检查和远程 Docker 场景。主服务依赖数据库和语言服务健康后再启动，能够降低初始化阶段的偶发失败；而远程 Docker 模式下可通过协议、地址、端口和 TLS 证书路径切换判题执行位置，说明项目在设计上已经把“业务服务部署位置”和“判题执行位置”解耦开来。即使当前论文阶段主要在单机环境中完成演示，这一实现仍然能够为后续扩展到独立判题节点或云主机判题提供直接基础。

\section{扩展能力验证与工程预留}

\subsection{异步判题链路的重构验证}

在当前主线实现中，平台已经完成了同步式代码提交、容器化编译运行和结果落库流程。为了验证后续扩展到独立判题 worker 的可行性，本文在重构验证阶段还尝试了“提交入队—后台执行—状态推送”的异步判题链路。该方案在提交创建后不立即在请求链路内完成全部判题，而是先生成 Submission 记录，再通过事件驱动方式触发后台判题任务，由独立执行单元完成编译、运行和结果写回。这个重构结果表明，当前平台的业务模型已经具备拆分为业务服务与判题服务的基础。

与同步方案相比，异步判题链路更强调过程状态的显式化。例如，提交在进入执行前可先处于 Pending 或 Queued 状态，随后流转到 Compiling、Running，最终达到 Accepted 或错误状态。这样的状态划分既提高了前端展示的可解释性，也为任务队列、节点扩容和异常重试提供了更清晰的基础。

\subsection{实时状态回传与多判题模式预留}

在扩展性验证方案中，平台还采用了实时状态回传机制，在判题状态变化时主动通知前端更新显示。这样一来，用户在提交代码后可以及时看到“已受理、编译中、运行中、完成”等阶段，而不需要频繁手动刷新页面。对于在线编程评测平台来说，这种机制既能改善交互体验，也能在高延迟或高负载场景下减少无效轮询带来的压力。

此外，扩展性验证也体现了更细粒度的判题模式建模思路。除一般的完整提交模式外，系统还预留了 sample、icpc、oi 等不同判题模式的区分空间，用于适配样例运行、传统 ACM/ICPC 风格评测和 OI 风格评测等场景。配合 Judge、JudgeRun 等中间实体，平台可以把提交级结果与测试用例级结果拆开记录，便于后续做课程教学统计、竞赛训练和错误分析。

\subsection{课程化教学能力的衔接基础}

虽然当前主线实现还没有把课程、作业和课程级运行环境配置完整纳入业务闭环，但平台已经具备一些可以继续衔接的基础。现有题库、提交、测试用例和分析结果等核心模型已经形成比较稳定的主链路，可以作为课程作业场景下 Assignment 与 Submission 关联的基础；现有 Docker 配置与远程 Docker 支持说明平台已经具备按配置切换执行环境的能力，后续可以继续细化到课程级或作业级配置；异步判题与实时回传的扩展验证也表明，平台后续可以继续朝“课程组织 + 后台调度 + 实时反馈”的方向扩展。

因此，从本文的成果边界来看，当前主线实现已经完成“题库—提交—判题—分析”的核心平台原型，而课程化教学组织和课程级运行环境配置则属于在此基础上可继续推进的增强方向。后续若将二者与现有主链路进一步结合，平台会更贴近真实高校程序设计课程的应用方式。

\section{本章小结}

本章围绕平台核心模块的实际落地情况，说明了数据模型、题库组织、在线提交、容器化判题、AI 辅助分析以及前端工作区等关键实现内容。从结果看，当前系统已经能够支持单机环境下的完整演示与运行，也为后续继续扩展保留了基础。对本科毕设而言，这种先完成完整原型、再为后续升级预留空间的处理方式更有利于保证成果可展示、论文可落地。
